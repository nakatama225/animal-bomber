# どうぶつボンバー — Python 版

動物同士が爆弾で戦う対戦ゲームの Python 実装。デスクトップで動きます。

**現在の状態：段階 7 まで**（段階 0 の骨組みと層の検査・乱数・座標・状態の要約・描画の重さの測定に、
盤面・移動・プレイヤーの入力、操作の記録と流し直し、フレームを回す輪と、フレームの間の待ち方の測定、
爆弾・誘爆・ブロック破壊、アイテム・一時的な状態・被弾と、起きたことを戻り値で返す形、ラウンドを
またぐ試合の進行と、キーボード・ゲームパッドの入力、5匹の動物の数値の違いと技、4段階の強さの
CPU、原型の手描きの絵と合成の音を足しました。1台で2人が遊べます。CPU を相手に選ぶ画面・名札や
ラウンドの間の画面はまだありません（盤面の上の1行に、ラウンド・勝ち数・体力を出しています）。
窓を開いて見たこと・音を鳴らして聞いたことはまだありません）。
段階ごとの主題は [docs/00-歩き方](docs/00-歩き方.md) にあります。

なぜ同じゲームを2つの言語で作るのか、2本が共有している設計判断は
[リポジトリ全体の README](../README.md) にあります。ここには Python 版に
固有のものだけを書いています。

## Design Choice — この版で採用する設計と、その理由

### 1. 描画エンジンは pygame-ce

pygame-ce・pyxel・arcade は比べたうえで選びました。raylib-py は、pygame-ce が重い場面で
間に合わなかったときの退避先として置いただけで、試していません。

| 候補 | 判断 | 決め手 |
|---|---|---|
| pygame-ce | 採用 | 原型が使っているグラデーション・半透明・曲線をそのまま再現できる。音を数値配列から合成できる |
| pyxel | 見送り | 色数が 256 に制限され、半透明とグラデーションが扱えない。原型の絵が再現できない |
| arcade | 見送り | 必要とする描画方式が macOS では古いバージョンで凍結されている。曲線・角丸・グラデーションを描く仕組みも無い |
| raylib-py | 退避先（使わない） | 試していない。下の測定で pygame-ce が間に合ったので、移らない |

#### 重い場面で間に合うかを、絵を描く前に測った

pygame-ce は描画を CPU で行います。重い場面で、1 フレームに使える時間（フレームバジェット。
1/60 秒 ≒ 16.67 ms）に間に合わないと分かるのが絵を描き終えたあとだと、エンジンを替えて絵を
書き直すことになります。そこで絵を描き始める前に、いちばん重い場面を窓を開かずに描いて測り、
pygame-ce で作り進めるかを決めました（作る前の Go/No-Go 判定）。描画の層はまだ無いので、
代わりの絵で同じ数の場面を描きました（[tools/bench_scene.py](tools/bench_scene.py)。測るコードは
段階 7 の前（b3e74d1）の `tools/bench_render.py`）。合格基準は [tools/bench_gate.py](tools/bench_gate.py)
にあります。段階 7 で描画の層ができたので、その層を通して測り直しました（下の「描画の層を通して
測り直した」。合格基準は変えていません）。

- 場面：延長戦で盤面がほぼ全部燃えている瞬間を想定し、原型で数えた爆風の最大 297 件と粒子の
  最大 105 個を同じフレームに重ねた（延長戦は切ったまま装備だけを最大にして回した 1 回で見た
  最大で、上限ではない）。粒子は四角い粒だけの行と光の玉だけの行を両方測る（測定の出力は、
  マスの大きさと粒子の種類の組み合わせごとに1行）
- 合格基準（測る前に決めた）：マス 60px の場面で、描画時間の 99 パーセンタイル（p99。速い順に並べて
  99% の位置の値。600 フレームなら遅いほうから 7 番目で、100 フレームに1回ある遅さ）が、しきい値
  8.33 ms（フレームバジェットの半分）以下。満たせば pygame-ce で作り進め、満たさなければ
  raylib-py への切り替えを考える
- あとから決めた、判定に使う行（マス 60 の四角い粒の行と光の玉の行の2行）の条件：爆風の位相を
  そろえ、窓の面へ 1 回貼る分も測る（レビューのあとに厳しい側へ直した）。全速で続けて描いて測る
  （初めからの測り方で、レビューのあとに決めごととして書いた）。2行の p99 の大きいほうを、判定に
  使う値にする（読み直しのあとに厳しい側へ直した。測る前は、重い側と見た光の玉の行だけで見ると
  決めていた）。薄れる絵を先に作っておく形で測る（測ったあとに決めた）
- 結果：**合格**（描画の層は、薄れる絵を先に作っておく形で書く。下の経緯）

段階 0 の測定（代わりの絵）：

| 描き方 | マス 60 の2行の大きいほうの 99 パーセンタイル（3 回） | しきい値 8.33 ms と比べて |
|---|---|---|
| 薄れる絵を、不透明度ごとに先に作っておく（採用） | 3.88・3.43・3.24 ms | 合格 |
| 薄れる絵を、貼るたびに薄める（参考） | 7.13・6.73・7.31 ms | 下回った（境目。下の経緯） |
| 先に作っておく形を、60 Hz に合わせて眠りながら回す（参考） | 7.89・4.02・3.90 ms | 下回った |

経緯：最初の測り方（爆風の位相を1件ずつ散らし、窓の面へ貼る分も測らない）では、貼るたびに
薄める形で、作り手が測った 4 回はどれも合格でした（光の玉の行で 4.31〜6.22 ms。負荷は記録して
いません）。レビューの間に、ほかの測定と並べて同じコードを負荷の中で走らせた 8 回では、5 回が
しきい値を超えました。レビューでは、測り方が軽く出る点が2つ見つかりました。1回の誘爆で出た爆風は
そろって薄れること、本物の窓の面がアルファの桁を持つ形式なら、そこへ直接描くと重くなることです
（窓を開かない測定では、窓の面の形式は分かりません）。そこで位相をそろえ、アルファの桁の無い面に
描いてから窓の面へ 1 回だけ貼る形にして、その 1 回も測りました（しきい値は変えていません）。

直した測り方で同じ日の 18 時台に測ると、貼るたびに薄める形（TypeScript 版の globalAlpha と同じ
考え方）は 3 回ともしきい値を超えました（マス 60 の2行の大きいほうの 99 パーセンタイルは 8.83・9.45・9.55 ms。CPU の時間の 99 パーセンタイルも
光の玉の行で 8.19〜8.59 ms）。同じ負荷のもとで位相だけを散らした 1 回は、光の玉の行で 7.57 ms でした。
薄めた絵を不透明度ごとに先に作っておき、薄めずに貼る形では 3 回とも収まったので（光の玉の行で
3.42・7.00・3.92 ms。光の玉の不透明度を 33 段に丸めていた版）、描画の層はこの形で書くことにしました。
重さの違いは、画素ごとの透明を持つ絵を、貼るときにさらに全体を薄めるかどうかだけです。

上の表と下の表の値は、そのあと読み直しで直した最終のコードで、19 時台に測ったものです。この時間帯は
機械が全体に速く、貼るたびに薄める形もしきい値を少し下回りました。貼るたびに薄める形はしきい値の境目に
あり、機械の状態で超えたり下回ったりします。先に作っておく形は、同じ時間帯でその半分ほどです。
見た目は同じになります。1 枚ごとの色の差は丸めの違いによる 1 でした（爆風 1 件と光の玉 1 個の場面。
テストでは 2 以下を確かめています）。爆風の芯が何枚も重なる所では足し合わさり、全部を描いた場面で
最大 6 でした（255 段のうち）。

### 2. 境界を、import の静的検査で守る

`domain/` の中では乱数・時刻・描画ライブラリを import できないよう、
`import-linter` と `ruff` の設定として書き、違反すると検査が失敗するようにしています。
TypeScript 版が型定義を外すことで実現しているものを、Python では
import の検査で実現します（理由は [docs/01-層とは何か](docs/01-層とは何か.md)）。

設定が実際に違反を見つけることは、テストの中で違反したファイルを書き出して
確かめています（`tests/boundary/test_guards.py`）。import を使わない書き方
（`round()`・`sum()`・小数の `**` など）は、ルールの層のファイルを構文木にして探す
テストで見つけます（`tests/boundary/test_builtins.py`）。

### 3. 乱数は標準の `random` を包まず、自前で書く

ゲームの結果に影響する乱数（`domain/core/rng.py`）は、標準の `random.Random` を
使わず、TypeScript 版と同じ mulberry32（32 ビットの整数1つを状態に持つ擬似乱数の
作り方）を自前で書いています。同じ種からは TypeScript 版と同じ並びが出ます。

| 採った案 | 採らなかった案 | 決め手 |
|---|---|---|
| 自前の mulberry32 | `random.Random` を包む | 包むと、ルールの層の `random` の禁止にこのファイルだけ例外が要る。また `random.Random` が Python の版をまたいで同じ並びを保証しているのは `random()` だけで、`shuffle` などは版によって変わりうる |

見た目だけの乱数（粒子・ちらつき・画面の揺れ）は同期も再現も要らないので、描画の層の
`CosmeticRng`（`presentation/cosmetic_rng.py`。中身は標準の `random.Random`）から引きます。

### 4. Python 固有の「同じ結果にならない」落とし穴に先に手を打つ

同じ入力で必ず同じ結果になること（決定性）は、通信対戦とリプレイの前提です。
Python にはこれを静かに壊す挙動がいくつかあり、実機で確認したうえで対策を決めています。

| 落とし穴 | 実際に起きること | 対策 |
|---|---|---|
| 文字列の集合（set）を順に取り出す順序 | プロセスを起動しなおすと順序が変わる | ルールの層では set を反復しない。順序が要る場所は list を使う |
| `round(2.5)` の結果 | 3 ではなく 2 になる（偶数丸め） | ルールの層で小数の丸めを使わない。体力は整数で持つ |
| 負の数の剰余 `-7 % 3` | 2 になる（言語によっては -1） | 剰余を1か所の関数に集約する |

いちばん厄介なのは1つ目です。原因が「順序」なので、**症状が出るまで時間がかかり、
出たときには原因から遠く離れた場所で壊れて見えます**。そのため、同じ処理を
文字列の hash（文字列から計算する整数。set の取り出し順を決める）の種を変えた2つの
プロセスで走らせ、結果の一致を確かめています
（`tests/determinism/test_hashseed.py`）。走らせるのは、台本どおりに操作した試合を記録して
流し直す処理です。この検査が効いていることは、わざと set を順に取り出す処理で2つの結果が
食い違うことを見て確かめています。

Python の版による違いは、試合の結果を固定値と比べるテスト（`tests/determinism/test_golden.py`）で
見ています。検査（`tools/verify.sh`）は pytest を 3.12 で走らせたあと、3.11 でもう一度
走らせます。そのため、リプレイの保存に Python の版を書いて、違えば流し直しを断る仕組みは
作っていません。版で結果が変わるなら、ルールの層の誤りとして直します。

### 5. 動物の能力は「網羅性を保証する」形で表現する

動物（`Animal`）と、突進・穴掘り・舌のばしといった行動中の状態（`Action`）、技が盤面に
残すもの（落とし穴・炎・跳ねる爆弾などの `Actor`）を、**取りうる種類を閉じた形**
（列挙と union）で定義しています。分岐は `match` で書き、どれにも当てはまらない場合を
型検査が見つけます。種類で分ける所は
[domain/abilities/techniques.py](src/animal_bomber/domain/abilities/techniques.py) などの
数か所に集めてあります。

新しい動物を追加すると、**対応を書き忘れている箇所がすべて型検査で失敗します**
（戻り値を返さない `match` でも失敗するよう、mypy の `exhaustive-match` を有効にしています）。
実行して踏むまで気づかない、ということが起きません。

試合を進める処理（移動・爆弾・拾う・被弾）は種類を見ず、行動中の状態の性質（位置を決める・
受ける傷の上限・爆弾を置けるか・足元のアイテムを自分で扱うか）だけを見ます。いちばん
特別扱いを誘う突進（移動・破壊・取得・被弾に同時に割り込む）も、共通の処理に突進の名前を
書かずに書けました。共通の処理に種類の名前が現れないこと（名前を書かずに型や属性で
見分ける書き方も含めて）は、テストが文字列で見張ります
（[tests/boundary/test_closed_kinds.py](tests/boundary/test_closed_kinds.py)）。

⚠️ 交換しているもの：追加のたびに既存の分岐に手を入れることになります。
TypeScript 版（[ts/](../ts/) — 既存を触らずに追加できる）と逆の性質です。
**開放性と網羅性のどちらを取るかは言語ごとに答えが違う**、というのがこの2本立ての主題です
（[docs/06-動物の技と閉じた種類](docs/06-動物の技と閉じた種類.md)）。

### 6. 盤面の時刻と、試合通算の時刻を、別の型にする

時刻は2つあります。盤面の時刻（段階 4 でラウンドを作ると、ラウンドごとに 0 へ戻る）と、
試合通算の時刻（試合が始まってから数えた tick 数。操作の記録と通信に使う）です。
TypeScript 版は初め盤面の時刻で操作を記録していて、2ラウンド目から記録が止まる不具合を
あとで直しました。この版は2つを最初から別の型（`typing.NewType` の `Tick` と
`MatchTick`）にしてあり、盤面の時刻をそのまま記録の時刻の所へ渡すと mypy が失敗します。
実行時はどちらもただの整数で、手間はかかりません。詳しくは
[docs/02-時間の刻みと記録](docs/02-時間の刻みと記録.md) にあります。

`MatchTick(world.now)` と包むと mypy は通るので、`src/` の中で `MatchTick(...)` を呼んでよい場所を、
試合通算の時刻を数える `MatchClock` と、保存した記録を文字列から戻す所の2つに限っています。
ほかで呼んだり、`MatchTick` を値として使ったり（別の名前に入れる・`typing.cast` に渡すなど）すると、
構文木を走査するテスト（`tests/boundary/test_match_tick.py`）が失敗します。名前を文字列で引く書き方や、
`type(clock.now)(x)` のように `MatchTick` の名前を書かずに値を作る書き方は見つけられません。

### 7. フレームは tick の境目に合わせて描き、補間をしない

実時間を「試合を何 tick 進めるか」に換えるのは、フレームを回す輪
（[src/animal_bomber/shell/loop.py](src/animal_bomber/shell/loop.py)）だけです。輪はフレームの
終わりに次の tick の時刻まで待ち、目を覚ましたら、前のフレームからの経過時間を tick の数に換えて
返します。次の tick の時刻は持ち越した端数から毎回計算し直すので、待ちが遅れても、次のフレームでは
tick の境目に戻ります。端数は整数（ナノ秒 × 1 秒あたりの tick 数）で持つので、何時間回しても
1 秒あたりの tick 数はずれません。

TypeScript 版はブラウザが決めた時刻に描くので、tick の境目と描く時刻のずれを使って、描く位置を
補間しています。この版は描く時刻を自分で決められるので、境目に合わせて描き、補間をしません。
これが成り立つのは、ゲームの速さが等倍か整数の倍速のときです。整数でない速さ（0.5 倍・1.5 倍など）
を作るなら、試合が tick の途中にいるフレームが出るので、TypeScript 版と同じく `step()` を呼ぶ回数の
端数（0.5 倍なら 1 フレームに半回ぶん）で補間します（`GameSpeed.progress`。輪が返すものは変えなくて
済みます）。
輪は generator にしてあり、呼び出し側は `for ticks in frames():` と書いて、`break` で抜けます。

1 回のフレームで何 tick 進めても試合の結果が変わらないことは、本物の輪を偽の時計で回して
確かめています（[tests/determinism/test_pacing.py](tests/determinism/test_pacing.py)。1 回に
進める tick の数を 0・1・2・7・15 と揺らす）。

#### フレームの間の待ち方を測り、眠ることにした

輪がフレームの間にどう待つかを、窓を開かずに比べて測りました
（[tools/bench_pacing.py](tools/bench_pacing.py)）。決め方は、測る前に
[tools/bench_pacing_rule.py](tools/bench_pacing_rule.py) に書きました。描画時間の p99 がしきい値
8.33 ms 以下、目を覚ました時刻の予定からの遅れの p99 が 2 ms 以下、1 tick 以外を進めたフレームが
1% 以下。3 回とも満たした候補のうち、CPU の使用率がいちばん低いものを選びます。

| 待ち方 | 描画の p50（中央値） / p99 | 遅れの p99 | 1 tick 以外 | CPU の使用率 | 判定 |
|---|---|---|---|---|---|
| 空回り（眠らずに時計を読み続ける） | 2.31〜2.33 / 2.98〜3.48 ms | 0.00 ms | 0 | 100% | 3 回とも合格 |
| 眠る | 5.52〜5.56 / 7.66〜7.78 ms | 5.48〜6.11 ms | 0 | 32〜33% | 3 回とも不合格（遅れ） → 下の理由で **採用** |
| 予定の 2 ms 前まで眠り、残りを空回り | 5.52〜5.54 / 7.57〜7.82 ms | 3.21〜3.48 ms | 0 | 33% | 3 回とも不合格（遅れ） |
| pygame の `Clock.tick(60)`（参考） | 6.14〜6.28 / 9.09〜10.03 ms | 20.69〜21.10 ms | 134〜135 | 30〜31% | 選ばない |

1 回の測定は、4 つの待ち方を 200 フレームずつ交互に 3 周したもの（待ち方ごとに 600 フレーム）で、
表は 3 回測った範囲です。描いた場面は、段階 0 の描画の重さの判定に使った行と同じ（代わりの絵の
[tools/bench_scene.py](tools/bench_scene.py)。マス 60・光の玉・薄れる絵を先に作っておく形）です。2026-10-03 の 16 時台に、1. の表と同じ機械で測りました。負荷は 1.9〜2.7
でした。遅れは、待つ関数が返った時刻と予定の時刻の差です。1 tick 以外は、600 フレームのうち 0 tick
か 2 tick 以上を進めたフレームの数です。

- 眠る待ち方は、目を覚ますのがいつも予定より遅れました。遅れの中央値は、どの回も 3.7 ms 前後で
  そろっていました。予定の 2 ms 前まで眠る形は、この遅れが 2 ms より長いので、多くのフレームで
  空回りを始める前に予定を過ぎていました（遅れの中央値は 1.7 ms で、0 になっていません）
- 眠る 2 つの形は、同じ描画が空回りの 2.4 倍ほど遅くなりました（p50 で 5.5 ms 対 2.3 ms）。予定の
  2 ms 前まで眠る形では空回りがほとんど起きておらず（CPU の使用率も眠る待ち方と同じ 33%）、最後に
  空回りを足すと描画の遅さが戻るかは、この測定では分かりません
- 遅れても、1 tick 以外を進めたフレームは 0 でした。遅れは描く時刻をずらしますが、1 tick ぶんより
  短ければ、進める tick の数は変えません。pygame の `Clock.tick(60)` は輪が決めた時刻を受け取らずに
  待つので、2 割を超えるフレームが 0 tick か 2 tick 以上になりました

決め方どおりなら空回りですが、眠ることにしました。

- 遅れの上限 2 ms は、フレームの時間（16.67 ms）の配分から置いた数で、遊んでいて感じるかどうかから
  決めた数ではありませんでした。このゲームはフレーム単位のずれを気にしないので、この上限を外しました
- 眠っても、1 tick 以外を進めたフレームは 0 で、試合の進み方は空回りと同じです。遅れ（p99 で 6.11 ms
  まで）と描画（p99 で 7.78 ms まで）を足しても、1 フレームに収まります
- 空回りは、待つ間も CPU のコアを 1 つ使い続けます。電池を減らし、機械を温めます。また Python の
  ループなので、待つ間、ほかの Python のスレッドは GIL の受け渡しを待たされます
- 予定の 2 ms 前まで眠る形も CPU の使用率は同じで、遅れは半分ほどでした。遅れを気にしないなら、
  空回りの部分の無い眠るだけの形で足ります

上限は測ったあとに外したので、決め方を測る前に書いた意味は、この判断には残っていません。

⚠️ 窓を開かずに測ったので、窓に出したとき、遅れた絵が画面の書き換えに間に合わず、動きが引っかかって
見えるかは分かっていません。遊べる段階（段階 4）で遊んでみて、引っかかって見えたら待ち方を見直します。

### 8. 1 tick の処理を分け、`step()` を順序の一覧にする

1 tick の処理を、動く・爆弾を置く・爆発する、のようにモジュールごとに分け
（`src/animal_bomber/domain/systems/`）、`step()` はそれを順に呼ぶだけにしています。並びがそのまま
「1 tick の中で何が先に起きるか」の一覧になります。なぜその順かは、`simulation.py` のモジュールの
説明に、並びと同じ番号で書いています。

| 採った案 | 採らなかった案 | 決め手 |
|---|---|---|
| 処理ごとのモジュールの関数 | TypeScript 版と同じく、処理ごとのクラスに `step()` メソッドを持たせる | 処理は状態を持たず、状態はすべて `WorldState` にある。持つものの無いクラスは、関数をまとめておく入れ物（名前空間）になるだけで、Python ではモジュールがその役をする |
| 爆風に触れた爆弾を待ち行列に積み、同じ tick の中で連鎖をまとめて処理する | 触れた爆弾の導火線を 0 にして、次の tick に爆発させる | 連鎖が 1 tick に1段ずつしか広がらず、爆風の出る tick が原型と変わる。同じ爆弾へ別の経路から爆風が二度届くので、積むときに印を付けて二度積まない |
| ブロックを壊すのは、1つの連鎖をすべて処理したあと | 爆風が届いたときに壊す | 途中で壊すと、1つの連鎖の中で、その先へ爆風が伸びるかが処理の順で変わる |

爆発の順（同じ tick に導火線の尽きた爆弾は置いた順、連鎖は積んだ順、向きは右・左・下・上）は
TypeScript 版と同じにしています。向きの順は原型と同じです。同じ爆弾に誘爆された2つの爆弾の爆風が
重なるマス（片方の爆弾のマスを含む）でも、当てたプレイヤーが原型と同じになるように、2026-10-04 に
上・右・下・左から替えました。順のそれぞれは `tests/systems/test_bomb.py` の順のテストで、
全体は、同じ盤面に同じ台本を流して 20 tick ごとにプレイヤー・爆弾・爆風・アイテム・盤面・識別子・
乱数を引いた回数・イベントの並びを比べる `tests/systems/test_simulation_ts.py` で確かめています。

⚠️ ブロックを壊すのを連鎖の終わりまで待っても、同じ tick の別々の連鎖のあいだでは、先に爆発した
連鎖が壊したブロックは、あとの連鎖からは空いて見えます（原型・TypeScript 版と同じ）。詳しくは
[docs/03-処理の分け方](docs/03-処理の分け方.md)。

### 9. 起きたことを戻り値で返し、受け取る側が `match` で種類を網羅する

`step()` は音も鳴らさず画面にも触らず、1 tick の中で起きたことを `SimEvent` の list で返します。
音と通知に変えるのは `presentation/presenter.py` で、受け取らなければ何も起きません。

| 採った案 | 採らなかった案 | 決め手 |
|---|---|---|
| 起きたことを戻り値の list で返す | ルールの処理の中から音と画面を呼ぶ（原型） | 画面も音も無い所でルールだけを動かせる。テストと強さの計測のための設定や、音を消す分岐をルールの層に持たずに済む |
| 種類ごとの frozen な dataclass の union | TypeScript 版と同じく、`type` という文字列の項目で見分ける | クラスそのものが種類の印になり、`match` のクラスの型で分けられる。項目の書き間違いが起きない |
| 受け取る側は `match` で分け、最後に `assert_never` を置く | 種類から処理への dict を引く | 種類を足すと、扱いを書き忘れた所が mypy で失敗する。dict だと、書き忘れは引いたときまで分からない |
| 一時的な状態は1つの入れ物（`EffectBag`）に入れ、作用はそれぞれの処理（移動・爆弾を置く・速さ）が見る | 状態ごとの作用を1か所に集める | 集めると、移動のことも爆弾のことも知っている大きな処理ができる。時間の進め方だけは共通なので1か所にまとめる |

段階 3 を作る途中で、TypeScript 版の不具合（1つの連鎖で2つの爆弾の爆風が同じブロックに届くと、
アイテムの抽選を2回引く）が見つかり、両方の版で直しました。原因と、同じ型の誤りを防ぐために
足したテストと決まりは、[docs/04-イベントを戻り値で返す](docs/04-イベントを戻り値で返す.md)の最後の節に
あります。

### 10. ラウンドをまたぐ進行は `step()` の外に置き、入力は1つの窓口にまとめる

ラウンドが決まったかを見るのはルールの層（`domain/systems/round.py`）、次の盤面を作るのは起動の層の
`GameSession`（`app/session.py`）です。キーボードとゲームパッドは、記録を流す窓口や CPU と同じ
`InputSource` として繋ぎます。

| 採った案 | 採らなかった案 | 決め手 |
|---|---|---|
| ラウンドの終わりを見たあと、盤面を作り直すのは `GameSession` | `step()` の中で盤面を作り直す | `step()` は「1回呼ぶと 1 tick 進む」だけを約束する。中で盤面が入れ替わると、記録を流し直したときに追えない |
| 決着のあと 120 tick 盤面を止めてから次を作る | 決まった tick に作り直す | 決着の爆発も倒れる瞬間も、描く前に盤面が切り替わって一度も描かれない |
| ラウンドの始まりは、爆弾のボタンを押していた扱い | 何も押していない扱い | 押したまま始まると最初の tick が押した瞬間になり、開始位置に爆弾を置いて詰む（原型にも同じ事故があった） |
| キーは位置（scancode）で持ち、押してすぐ離した爆弾と技のキーも 1 tick は押したことにする | キーに書かれた文字で持ち、押されているキーだけを見る | 配列で記号の位置が変わらない。1回の描画の間に押して離した爆弾のキーを落とさない（原型と同じく、向きのキーは押されているかだけ） |

詳しくは [docs/05-試合の進行と入力](docs/05-試合の進行と入力.md)。窓を開いて遊んでの確かめ
（キーボードとパッドの実機）はまだです。

### 11. 原型の絵と音は記録した正解と突き合わせて写し、毎フレームは取っておいた絵を貼る

| 採った案 | 採らなかった案 | 決め手 |
|---|---|---|
| 描く関数は、原型の canvas の命令の列（順・値・見た目の乱数を引く順）まで写し、原型を node で読み込んで記録した列と突き合わせる | TypeScript 版の描画から写す | 正解は原型。TypeScript 版には原型と違えた所がある（爆弾の脈打ちの位相・炎の通った跡など） |
| 毎フレームは、段に丸めた入力ごとに1回だけ描いて取っておいた絵を、原型と同じ順に貼る | 描く関数を毎フレーム呼ぶ（canvas の写しに描く） | 間に合わない。描く面の全体を描くと、マス 60 で 100MB の配列を使う |
| 段の数は、先にずれの上限（px か色の段）を決めて出し、上限をテストで確かめる | 見た目で段の数を決める | 段を粗くしたことに、あとから気づけない |
| 粒子・画面の揺れ・歩いた距離などは、ルールの層のイベントと前の tick との比べから、描く側で数える | ルールの層に粒子などを持たせる（原型と同じ） | 試合の結果に関わらない。ルールの層に入れると、通信対戦で突き合わせるものが増える |
| 音は、原型が Web Audio に入れていた予定を仕様の式で読んで合成し、起動時に焼く | 鳴らすたびに合成する | 長い音は1つに 18 ms ほどかかり、1フレームに収まらない |

原型の不具合も、絵に出るものは写しました（落とし穴にはまったプレイヤーを描くと、そのフレームの
そのあとのプレイヤーと炎が、そのプレイヤーの薄さで描かれる）。どこまで写し、どこを作り直したかと、
原型と違うまま残した所は [docs/08-絵と音](docs/08-絵と音.md) にあります。

## How-to — 動かし方

Python 3.11 以上と [uv](https://docs.astral.sh/uv/) が要ります
（`.python-version` で 3.12 を選んでいます）。

```sh
cd py
uv sync
uv run tools/verify.sh   # ruff → 整形 → mypy → import-linter → pytest（3.12 と 3.11）
uv run python tools/bench_render.py   # 描画の重さを測る（本物の描画の層で描く。窓は開きません。1 分ほど）
uv run python tools/bench_render.py --first-draw   # 試合の前に絵を描いておく時間を、絵の種類ごとに測る
uv run python tools/bench_pacing.py   # フレームの間の待ち方を比べる（窓は開きません。2 分半ほど）
```

遊ぶときは次のとおりです（1台で2人。1P は WASD と Space、2P は矢印と Enter。どちらも
ゲームパッドでも動きます。窓を閉じるか Esc で終わります）。起動すると「じゅんびちゅう」と出て、
試合で使う絵を描いておくあいだ（マス 60 で 3 秒ほど）待ちます。

```sh
uv run python -m animal_bomber.app.main
```

ルールの層は、`uv run python` の対話の画面から読み込んで 1 tick ずつ進められます（例は
[docs/02-時間の刻みと記録](docs/02-時間の刻みと記録.md) の最後の節）。

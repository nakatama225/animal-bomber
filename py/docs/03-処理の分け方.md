# 処理の分け方

段階 2 で爆弾を足し、1 tick の処理を「動く・爆弾を置く・爆発する」に分けました。
段階 3 で「拾う・被弾する・状態の時間を進める」を足しています。そのあと、「勝手に設置」の
拍に置く処理を、ボタンの爆弾から分けて動く前に置きました（原型と同じ時期に置くため）。
段階 5 で、技（振る舞いを進めて新しく技を出す）と盤面の物を進める処理を足しました。
そのあと、並びを原型の update と同じにし、「プレイヤーごとにいくつかの処理を済ませて
から次のプレイヤーへ進む」輪を2つ持つ形になりました（下の 1. と 2.）。段階 8 で、外周の
プレイヤーを動かして葱を撃つ処理（2. の先頭）と、外周を閉じる処理（8.）を足しました。
`domain/systems/simulation.py` の `step()` は、分けた処理を順に呼ぶだけになっています
（下の例のコメントは、説明のために足したものです。時刻を1つ進める行は省きました。
起きたイベントを集めて返す部分は
[04-イベントを戻り値で返す](04-イベントを戻り値で返す.md)）。

```python
def step(world, inputs):
    events = []
    # 1. プレイヤーごとに：焼けた舌を戻す → 状態の時間を減らす → 振る舞いを進める
    #    → 「勝手に設置」の拍を見る
    for player in world.players:
        events.extend(step_owned_actors(world, player))
        advance_effects_for(player)
        events.extend(advance_for(world, player))
        events.extend(autobomb_for(world, player))
    # 2. プレイヤーごとに：外周のプレイヤーは外周を動いて葱を撃つ → 動く
    #    → ボタンの爆弾を置く → 技のボタンを見る → 拾う
    for player in world.players:
        player_input = inputs[player.id]
        events.extend(lane_step_for(world, player, player_input))
        move_player(world, player, player_input)
        events.extend(place_for(world, player, player_input))
        events.extend(watch_for(world, player, player_input))
        events.extend(pick_up_for(world, player))
    # 3. 通り抜けを外し、盤面の物（落とし穴・葱・炎・撒く本体・跳ねる爆弾）を
    #    actor_turn の順に進める。同じ番のものを全員進めてから当たりを見る
    release_pass_through(world)
    events.extend(step_actors(world))
    # 4. 溶けきったもの・残る長さを過ぎたアイテムを消す
    events.extend(remove_expired(world))
    # 5. 導火線を進め、尽きた爆弾を連鎖ごと爆発させる
    advance_fuses(world)
    events.extend(detonate_expired(world))
    # 6. 爆風の残り時間を進める
    expire_blasts(world)
    # 7. 爆風に触れたプレイヤーの体力を減らし、伸びている舌が焼けたかを見る
    events.extend(step_damage(world))
    events.extend(after_damage(world))
    # 8. 残り時間が短くなっていれば外周を閉じる
    events.extend(close_lanes_if_due(world))
    # 9. この tick の入力を、次の tick のために前の入力として残す
    _remember_inputs(world, inputs)
    return events
```

## 並びがそのまま「1 tick の中で何が先に起きるか」になる

処理の順は結果を左右します。原型は1つの `update()` の中に全部が書かれていて、どこで
何が先に起きるかは、長い関数を上から読まないと分かりませんでした。この版は、並びを
`step()` の数行に集めました。並び自体は原型と同じで、なぜそうなるかは、`simulation.py`
のモジュールの説明に、並びと同じ番号で書いています。

- **ボタンの爆弾は動いてから置く**。押した tick にマスの境目をまたいだら、動いたあとの
  マスに置く。1人ずつ「動く → 置く」を済ませるので、番号の小さいプレイヤーが置いた
  爆弾は、同じ tick にあとから動くプレイヤーの壁になる
- **技は動いてから出す**。技が出る tick に向きを押せば、押した向きへ出る。振る舞いの最中も
  ボタンを見るので、振る舞いが終わった tick のうちに押せば、次の技が出る
- **「勝手に設置」は動く前に置く**。拍の tick にマスの境目をまたいでも、今までいたマスに
  置く。全員ぶんをボタンの爆弾より先に置くので、同じ tick に置く順も原型と同じになる
- **拾うのは爆発より先**。爆発する tick に踏み込んだアイテムは、焼ける前に拾える。落とし
  穴に落ちるのも拾ったあと（穴が滑りを消すので、穴の上のバナナを踏んでも滑らない）
- **状態の時間はプレイヤーごとに、振る舞いを進める前に減らす**。番号の小さいプレイヤー
  の技で番号の大きいプレイヤーに状態がかかると、その tick のうちに1回減る
- **被弾は拾うよりあと**。被弾して足元へ吐き出したアイテムを拾うのは、次の tick
- **入力を前の入力として残すのは最後**。「押した瞬間」の判定には前の tick の入力を使う。
  途中で残すと、そのあとの処理から見て「押した瞬間」が消える

並びを原型に揃える前（段階 5 まで）は、技を始めるのが動く前、拾うのが爆発のあと、状態の
時間を減らすのが最後、振る舞いを進めた tick は技のボタンを見ない、と原型と違っていました。違う所は原型に揃えるのがこの版の決まりで、
揃えたあとの並びは、原型を画面なしで動かして測った答えと比べるテスト
（`tests/systems/test_tick_order.py`）で確かめています。

## 爆弾と爆発を別の処理にした理由

導火線を進めるのは1つの爆弾の話ですが、爆発は連鎖でまとめて起きます。1つの爆弾の
爆風が別の爆弾に触れると、そちらも同じ tick に爆発します（原型と同じ）。触れた爆弾の
導火線を 0 にして次の tick に爆発させる形にすると、連鎖が 1 tick に1段ずつしか広がらず、
爆風の出る tick が原型と変わります。そこで `systems/blast.py` は、触れた爆弾を待ち行列に
積み、連鎖が尽きるまで 1 tick の中でまとめて処理します。同じ爆弾へ別の経路から爆風が
二度届くので、積むときに印を付けて、二度積まないようにしています。

連鎖の中にも、結果を左右する順があります。

| 順 | 決め方 | 変えると |
|---|---|---|
| 同じ tick に導火線の尽きた爆弾 | 置いた順（`world.bombs` の並び） | 爆風の識別子と並び。さらに、先の連鎖が壊したブロックの先へ、あとの連鎖の爆風が伸びるか（爆風の届く範囲と盤面） |
| 連鎖の中 | 待ち行列に積んだ順 | 爆風の識別子と並び。爆風が重なったマスで当てたプレイヤー |
| 爆風を伸ばす向き | 右・左・下・上（`core/coord.py` の `SCAN_ORDER`。原型と同じ。`Direction` の定義順（上・右・下・左。TypeScript 版の `DIRECTIONS` と同じ）とは別に持つ。CPU の経路探しも同じ順） | 爆風の識別子と並び。誘爆した爆弾を積む順と、爆風が重なったマスで当てたプレイヤー |
| ブロックを壊す時 | 1つの連鎖をすべて処理し終えたあと | 1つの連鎖の中で、壊れたブロックの先へ爆風が伸びるかが、処理の順で変わる |

ブロックを壊すのを連鎖の終わりまで待つので、1つの連鎖の中では、ブロックの先へ爆風が
伸びるかは処理の順に左右されません。ただし、同じ tick の別々の連鎖のあいだでは、先に
爆発した連鎖が壊したブロックは、あとの連鎖からは空いて見えます（原型・TypeScript 版と
同じ）。だから、同じ tick に導火線の尽きた爆弾の順は、爆風の届く範囲まで変えます。

TypeScript 版と同じ順にしてあります。順のそれぞれは `tests/systems/test_bomb.py` の
順のテストで確かめ、全体は、段階 3 の台本を TypeScript 版（同じコミットの `ts/` の写し）
にも流して 20 tick ごとに
プレイヤー・爆弾・爆風・アイテム・盤面・識別子・乱数を引いた回数・イベントの並びを比べる
`tests/systems/test_simulation_ts.py` で確かめています。

⚠️ 1つの連鎖の中で、別々の爆弾の爆風が同じブロックに届いても、壊すのは1回です。壊れた
ブロックごとにアイテムを落とす抽選を引くので、2回壊すと同じマスにアイテムが2つ出ます。
TypeScript 版は段階 3 から 2026-10-04 まで、そうなっていました（経緯は
[04-イベントを戻り値で返す](04-イベントを戻り値で返す.md) の最後の節）。

## 「通れるか」の問いは1か所にまとめる

あるマスを通れるかは、どのプレイヤーが見るかによって違います。爆弾のマスは、置かれた
瞬間に体の中心がそのマスにあったプレイヤーだけが、そこから出るまで通れます。段階 5
で、壊せるブロックの中を進める動物も入りました（`passes_soft_block`）。この問いを
移動の処理と CPU の判断（段階 6）が別々に書くと、片方だけ直したときに食い違います。そこで、読むだけで何も
書き換えない問い合わせを `domain/query/board.py` に集め、移動の当たり判定もそこを
通します。

⚠️ 移動では、体がそのマスにかかっている間は、誰でもそのマスを通れます（当たり判定が、
体の重なっているマスを見ないため）。爆弾の通り抜けの対象かどうかが答えを変えるのは、
問い合わせ（`is_solid_for`）だけで、段階 2 の移動の結果には効きません。

## TypeScript 版との違い

TypeScript 版は処理ごとに `BombSystem` のようなクラスを作り、`step()` メソッドを持たせて
います。この版はクラスを作らず、モジュールの関数にしました。処理そのものは状態を持たず、
状態はすべて `WorldState` にあるためです。持つものの無いクラスは、関数をまとめておく
入れ物（名前空間）になるだけで、Python ではモジュールがその役をします。

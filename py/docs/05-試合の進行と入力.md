# 試合の進行と入力

段階 4 で、2人で遊べるようになりました。足したのは2つです。ラウンドをまたいで試合を
進めること（ラウンドの終わり・勝ち数・次の盤面）と、キーボードとゲームパッドを、
CPU や記録を流す窓口と同じ資格で試合に繋ぐことです。

---

## 試合の進行は `step()` の外に置く

ラウンドが決まったかを見るのは `domain/systems/round.py`、次の盤面を作るのは
`app/session.py` の `GameSession` です。`step()` には並べていません。

```python
session = GameSession(config, sources)
for _ in range(ticks):
    events = session.tick()  # 1 tick 進む。ラウンドが決まれば、待ってから次の盤面を作る
```

`step()` は「1回呼ぶと盤面が 1 tick 進む」だけを約束しています。その中で盤面が丸ごと
入れ替わると、記録を流し直したとき、どの tick で何が起きたかが追えなくなります。
盤面を作り直す処理は、ルールの層ではなく、起動の層（`app/`）が持ちます。`GameSession` は
ルールを持たず、ルールの層の部品を呼ぶ順だけを知っています（TypeScript 版と同じ形）。

### ラウンドごとの種は、試合の種から導く

```python
seed_for_round(config, round_number)  # (seed + round * 0x9E3779B1) & 0xFFFFFFFF
```

試合の種1つから全ラウンドの盤面が決まるので、「3ラウンド目だけ見たい」も設定だけで
足ります。TypeScript 版の `>>> 0` と同じく、2^32 で割った余りにしています。

### 決着のあと、盤面を止めて待つ

ラウンドが決まった tick に次の盤面を作ると、決着をつけた爆発も、倒れる瞬間も、画面に
1度も描かれません（描く前に盤面が切り替わる）。決まったあとは前の盤面を止めたまま
`ROUND_INTERMISSION`（120 tick）待ち、そのあと次の盤面を作ります。待つ間は入力を
集めず、イベントも返しません。TypeScript 版も、段階 4 のあとでこの形に直しました。

### 試合通算の時刻は、待つ間も進む

盤面の時刻（`world.now`）はラウンドごとに 0 へ戻り、待つ間は止まります。記録と通信に
使う試合通算の時刻（`MatchTick`）は、`GameSession.clock` が待つ間の tick も数えます
（[02-時間の刻みと記録](02-時間の刻みと記録.md) の2つの時刻）。

### ラウンドの始まりは、爆弾のボタンを押していた扱い

爆弾は「前の tick に押していなかったボタンを押した瞬間」に置きます。ラウンドの始まりの
「前の tick」を何も押していない扱いにすると、爆弾のボタンを押したまま始まったとき、
最初の tick が押した瞬間になり、開始位置に爆弾を置いて詰みます。待つ間に押し続けて
いれば、実際の試合でも起きます。そこで `create_world` は、前の tick を爆弾のボタンを
押していた扱い（`HELD_AT_ROUND_START`）にします。押したまま始まったボタンは、一度離して
押し直すと効きます。原型も TypeScript 版も、同じ事故を直しています。

テストの盤面（`tests/helpers.py` の `make_world`）は、ラウンドの途中の盤面として作ります
（前の tick は何も押していない）。そうしないと、押した瞬間を見るテストがどれも 1 tick
待つ形になります。

### 2人のときは対角から始める

1台で2人が遊ぶときは、左上と右下の対角から始めます（`DUEL_SPAWN_ORDER`。原型の 2p
モードと同じ）。人数ではなく遊び方で決まる（原型の LAN 対戦は番号の順のまま）ので、
`create_world` の既定にはせず、試合の設定（`MatchConfig.spawn_order`）で渡します。

## 入力の窓口

ルールの層が知っているのは、tick ごとに `PlayerInput` を返す窓口（`InputSource`）
だけです。段階 4 で、キーボードとゲームパッドの窓口を足しました。どちらも `shell/` に
あり、pygame を触るのはこの層だけです。

| 窓口 | 置き場所 | 段階 |
|---|---|---|
| キーボード（`KeyboardSource`） | `shell/keyboard.py` | 4 |
| ゲームパッド（`GamepadSource`） | `shell/gamepad.py` | 4 |
| 2つを合わせる（`EitherSource`） | `domain/input/sources.py` | 4 |
| 記録を流す | `net/input_log.py` | 1 |
| CPU（`CpuInputSource`） | `ai/source.py` | 6 |
| 通信で届いた操作 | `net/` | 9 |

1人がキーボードとパッドのどちらでも遊べるよう、`EitherSource` で2つを合わせます
（どちらかで押していれば押したことにする）。

### キーは位置で持つ

割り当ては、キーに書かれた文字ではなく、キーボードの上の位置（SDL の scancode）で
持ちます。文字で持つと、配列（日本語配列と英語配列など）によって `/` や `.` の位置が
変わります。

### 押してすぐ離した爆弾と技のキーも、1 tick は押したことにする

1回の描画の間に届いたイベントを、まとめて読みます。押してから離すまでが 1 tick より
短いと、押したことと離したことが同じ回に届き、押されているキーだけを見ると、押した
こと自体が消えます。`KeyboardWatcher` は、前の tick から押されたキーを別に覚え、爆弾と
技のキーは、離していても次の 1 tick は押していたことにします（`end_tick` で忘れる）。

原型と同じ範囲です。原型も押した瞬間を別の一覧に覚えていましたが、その一覧で見るのは
爆弾と技だけで、向きは押されているキーだけで見ます（押してすぐ離した向きのキーでは
動きません）。

### パッドは、決まった並びに直したものだけを扱う

SDL のゲームコントローラーの仕組みが、製品ごとのボタンの並びを決まった名前（A・B・
十字の上 など）に直します。製品ごとの対応表を持たずに済みます。

- スティックは傾きの大きいほうの軸だけを見ます。軸ごとにしきい値を当てると、真上から
  少し倒しただけで横にも入り、移動の側が横を先に見るので、横へ歩きます
- 倒すしきい値（0.5）と戻りのしきい値（0.35）を分けて、境目でちらつかないようにします
- 1台で使うパッドは1つだけです（段階 10 から。原型と TypeScript 版も同じ）。どのパッドを
  使うか（`PadChoice`）を1つ作り、メニューと試合の窓口で分け合います。繋がっている順で
  最初のパッドをつかみ、外れるまで使い続けます。ほかのパッドが繋がっても移りません
- パッドを試合に繋ぐのは、1人で遊ぶとき（1人 vs CPU×3）と通信対戦だけです。2人で遊ぶ
  ときは、2人とも左右に分けたキーボードで操作します（パッドを2人の左右の組に足すと、
  2人とも同じパッドで動きます。原型 L3570。原型は「1台に2つ挿して2人」を、作り直す所が
  多いのでやらないと決めていました）
- 段階 4〜9 は、2人がそれぞれのパッドで遊べるように、どのパッドをだれが使っているか
  （`PadClaims`）を2人の窓口で共有していました。`PadClaims` は段階 4〜9 の形として残して
  あり、いまは `GamepadSource` の既定とテストだけが使います

パッドを読む部分（`ControllerReader`）を窓口の外に置き、窓口は読んだ結果だけを
受け取ります。どのパッドを使うか・スティックの向きは、パッドを繋がずにテストできます。

`PadChoice` と `PadClaims` は、パッドを見分ける番号が、繋いでいる間は変わらないことに
拠っています。`ControllerReader` は SDL のインスタンス番号を使い、開いた直後に控えます。
pygame の `Controller.id` は開いたときの並びの番号で、前のパッドが外れると詰まるので
使いません（使うと、前のパッドを抜いたとき、うしろのパッドが前のパッドの番号を引き継ぎ、
使っているパッドが入れ替わります）。抜き差しは、SDL の仮想パッドを使ってテストしています
（`tests/shell/test_gamepad.py`。実機のパッドではない）。

## TypeScript 版との違い

TypeScript 版の列は、段階 4（8d00107）と、いまの形（HEAD）で違うものを書き分けています。

| | TypeScript 版 | この版 | 理由 |
|---|---|---|---|
| 窓口の渡し方 | `GameSession.attach()` であとから足す（段階 4 もいまも） | 作るときにまとめて渡す（`InputGatherer` が、同じプレイヤーの窓口が2つあれば止める） | 繋ぎ忘れと二重の繋ぎを、試合を始める前に見つける |
| 押してすぐ離したキー | どのキーも押されているかだけを見る（消えうる。段階 4 もいまも） | 爆弾と技のキーは、次の 1 tick は押したことにする | 原型と同じ。1回の描画の間に押して離した爆弾のキーを落とさない |
| パッドの割り当て | 段階 4：窓口ごとに使うパッドを覚える（2つ作ると、どちらも最初に見つかったパッドを使う。起動の入口はパッドを繋いでいない）。いま：`PadChoice` 1つを全部の窓口で分け合う（使うパッドは1つ） | 段階 4〜9：`PadClaims` を2人で共有した。段階 10 から：`PadChoice` 1つをメニューと試合で分け合い、パッドを試合に繋ぐのは1人で遊ぶときと通信対戦だけ | 段階 4〜9 は、2人がそれぞれのパッドで遊べるようにした。段階 10 で原型に合わせた（パッドは1台に1人ぶん。2人の左右の組に足すと、2人とも同じパッドで動く。原型 L3570） |
| 2人の開始位置 | 段階 4：番号の順。いま：2人なら既定で対角（`createWorld`） | 試合の設定で渡す | 原型でも、遊び方（1台か LAN か）で決まる |

## 遊べるようにするための絵

段階 4 から段階 6 までは、盤面・爆弾・爆風・アイテム・プレイヤーを、色を付けた四角と丸で
描く仮の絵で遊べるようにしていました。段階 7 で、原型の絵を写した描画の層
（`presentation/render/renderer.py`）に置き換えました（[08-絵と音](08-絵と音.md)）。
段階 10 で、タイトルから遊び方を選ぶ画面と、ラウンドの幕（1台の試合は原型どおりボタンで
送る）を足しました（[11-画面と設定](11-画面と設定.md)）。起動は次のとおりです。

```sh
uv run python -m animal_bomber.app.main   # タイトルから遊び方を選ぶ。窓を閉じると終わる
```

1台の試合のラウンドの幕は、`GameSession.start_next_round` で決着のあとの待ちを切り上げて
送ります。幕が出ている間は試合を進めません（進めると、待ち（`ROUND_INTERMISSION`）が尽きて
勝手に次のラウンドの盤面ができる）。通信対戦は、全員が同じ tick に次のラウンドへ進む必要が
あるので、待ちを進めて幕を消します。

## 確かめていないこと

窓を開いて遊んでの確かめは、Mac の前で行います。テストは SDL の dummy ドライバと、作った
イベント・パッドの状態で行っていて、次は確かめていません。

- 実際のキーボードで、日本語の入力（変換）を止めたまま文字のキーが届くか
  （`app/main.py` の `pygame.key.stop_text_input()`）
- 実際のパッドを `ControllerReader` で読めるか（ボタンの名前・スティックの向き・
  HOME ボタンが届くか。抜き差しの番号の扱いは、SDL の仮想パッドで確かめた）
- 遊んで、動きが引っかかって見えないか（README の Design Choice の 7. の待ち方）

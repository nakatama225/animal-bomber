# イベントを戻り値で返す

段階 3 でアイテム・一時的な状態・被弾を足し、1 tick の中で起きたことを `step()` の
戻り値で返す形にしました。

## 原型は、ルールの処理の中から音と画面を呼んでいた

原型の `update()` は、効果音（`SE.explode()` など）・画面の名札の書き換え
（`renderCards()`）・短い通知（`toast()`）を、ルールの処理の中から直接呼んでいました。
そのため、画面も音も無い所でルールだけを動かすことができません。CPU の強さを何千試合も
測ろうとすると、音を鳴らしながら実時間で回すことになります。

この版のルールの層は、起きたこと（爆弾が置かれた・ブロックが壊れた・プレイヤーが
倒れた、など）を `SimEvent` の list にして返すだけです。音を鳴らすか、通知を出すか、
何もしないかは、受け取った側が決めます（`presentation/presenter.py`）。

```python
events = simulation.step(world, inputs)
presenter.consume(events)  # 遊ぶとき
```

テストや強さの計測では、受け取らなければ何も鳴りません。音を消す設定も、テスト用の
モードも、ルールの層には要りません。

## 種類ごとにクラスを分け、union でまとめる

TypeScript 版は、`type` という文字列の項目で種類を見分ける形（判別可能ユニオン）に
しています。この版は種類ごとに frozen な dataclass を作り、`SimEvent` をその union に
しました（`domain/events.py`）。クラスそのものが種類の印になるので、`type` の項目は
要りません。

受け取る側は `match` で種類ごとに分け、最後に `assert_never` を置きます。

```python
match event:
    case BombPlaced():
        sounds.play(SoundName.PLACE)
    case Exploded(count=count):
        sounds.play(SoundName.EXPLODE, count)
    # ……ほかの種類……
    case _:
        assert_never(event)
```

種類を1つ足すと、扱いを書き忘れた `match` が型検査（mypy）で失敗します。`assert_never`
には「ここへは何も届かない」型しか渡せないので、扱っていない種類が残っていると型が
合わなくなるためです。足した側が、音を当てるか・何と出すかを必ず1度は決めることに
なります。⚠️ `case _:` に `assert_never` 以外を書いて黙らせないでください。

## 一時的な状態は1つの入れ物に入れ、作用はそれぞれの処理が見る

バナナ（滑る）・たまねぎ（泣いて動けない）・うんこの6つの悪い状態は、残り時間を1つの
入れ物（`state/effects.py` の `EffectBag`）に入れます。原型ではこれらがプレイヤーの
個別の項目としてあちこちの処理に散っていました。

作用は、それぞれの処理が自分の受け持ちの中で見ます。

| 状態 | 見る処理 |
|---|---|
| 泣いて動けない・そうさ反転・滑る・とまれない | 移動（`systems/movement.py`） |
| 爆弾おけない・勝手に設置・爆風1マス | 爆弾を置く（`systems/bomb.py`） |
| 超スロー・とまれない（速さの下限） | 速さ（`state/player.py` の `speed_of`） |

時間を進めるのだけは全部の状態に共通なので、`systems/effects.py` にまとめています。
作用まで1か所に集めると、移動のことも爆弾のことも知っている大きな処理ができてしまいます。

同じ状態を重ねて踏むと、残り時間に足します（上書きしない）。上書きだと、何個踏んでも
1つぶんの時間で済み、踏むコストが頭打ちになります。足し続けると復帰できなくなるので、
基本の秒数の 3 倍で止めます。

## TypeScript 版と同じ結果になることの確かめ

`tests/systems/test_simulation_ts.py` は、TypeScript 版の段階 3 と同じ盤面に同じ台本を
流し、20 tick ごとに、プレイヤー・爆弾・爆風・アイテム・盤面・識別子・乱数を引いた
回数と、その間のイベントの並びを比べます。台本は3つで、3つ目は盤面にアイテムを並べ、
ときどき向きのボタンを全部離します。悪い状態が8つともかかり、手を離しても滑る・
とまれないで進む・壁で滑りが終わる・反転して進む、をどれも通る種を選んであります。

## 試合を通して崩れない約束

場面を1つ組み立てるテストは、組み立てた場面しか見ません。`tests/systems/test_match_invariants.py`
は台本どおりの試合を流し、毎 tick「同じマスにアイテムが2つ並ばない」を確かめます。
アイテムを置く処理は、どれもそのマスにアイテムが無いことを前提にできるからです（被弾
して吐き出すときはアイテムのあるマスを飛ばし、壊れたブロックから落とすときは、いま
壊したブロックのマスに置く）。思いつかなかった崩れ方も、台本の中で起きれば捕まります。

## TypeScript 版で見つかった、抽選を2回引く不具合（2026-10-04）

段階 3 を作る途中で、TypeScript 版の不具合が見つかりました。1つの連鎖で2つの爆弾の
爆風が同じブロックに届くと、そのブロックからアイテムを落とす抽選を2回引いていました。
アイテムの出る確率が 55% から約 80% に上がり、同じマスにアイテムが2つ重なることも
ありました。CPU どうしの試合では、種 0〜9 のすべてで起きていました。

原型の、ブロックを壊す関数の1行目は `if (tileAt(x,y)!==SOFT) return;` です。壊すブロック
の一覧には同じマスが2回入りますが、1回目でマスが空くので、2回目はこの行で帰り、抽選
まで届きません。重なりを止めていたのは一覧ではなく、この1行でした。

TypeScript 版は段階 2 でこの関数を移さず、ループの中にマスを空ける処理を直接書いたので、
この1行が消えました。そのときは2回空けても結果が同じで、何も起きません。段階 3 で同じ
ループに抽選を足したときに、2回引くようになりました。段階 3 の差分には、重なりを許す
一覧の作りが出てこず、テストも爆弾1つの場面だけで、2つの爆弾の爆風が同じブロックに届く
場面がありませんでした。

この版は段階 2 の時点で、その場所に「同じマスが2回入る。いまは害が無いので、段階 3 で
決める」と書いておいたので、段階 3 で抽選を足す前に気づけました。

直したこと：

- 両方の版で、壊れたブロックの一覧に入れるときに同じマスを除く
- 並んだ2つの爆弾の爆風が同じブロックに届く場面のテスト（`tests/systems/test_bomb.py`）
- 上の「試合を通して崩れない約束」のテスト（TypeScript 版は CPU どうしの試合で確かめる）
- 原型から処理を移すときの決まりを、リポジトリの `AGENTS.md` に書いた（入口で早く帰る
  確かめを黙って消さない／いま害の無い重なりは、その場所に何を足すと害になるかまで書く）

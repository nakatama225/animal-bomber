# どうぶつボンバー

動物同士が爆弾で戦う対戦ゲーム。家族で遊ぶために作ったブラウザゲームを、
TypeScript と Python の2つで設計から作り直します。

| | 中身 | 読むところ |
|---|---|---|
| 原型 | 単一の HTML ファイル。ブラウザで開けばそのまま遊べる | [legacy/](legacy/) |
| 中継サーバ | LAN 対戦の中継（Python）。ゲームのルールを持たない | [server/](server/) |
| TypeScript 版 | ブラウザで動く（Vite） | [ts/](ts/) |
| Python 版 | デスクトップで動く（pygame-ce） | [py/](py/) |

原型と中継サーバは動きます。TypeScript 版と Python 版は実装中です。

---

## Why — なぜ同じゲームを2つ作るのか

原型はブラウザで動く単一の HTML ファイル（6,119 行）です。動くものを最短で
作ることを優先した結果、次の3つが1つの関数の中で混ざっています。

- ゲームのルール（爆弾が何秒で爆発するか、どのマスが壊れるか）
- 画面の描画（Canvas への線と色）
- 実時間（フレーム間の経過ミリ秒）

混ざっていること自体はすぐには困りません。困るのは、後から
「対戦相手を別の端末にしたい」「AI の強さを1万試合で測りたい」と思ったときです。
ルールだけを取り出して動かす方法がないため、どちらも画面と実時間を巻き込んだ
大改造になります。

この2本は、**同じゲームを、境界を引き直して作る**ことを目的にしています。移植ではありません。

### 2つ作ると何が見えるか

設計の考え方 — ルールと画面を分ける、時間の進みを固定する、入力の出どころを
1つにまとめる — は言語が変わっても同じです。一方で、**その考え方を実現する
最適な書き方は言語ごとに違います**。

「動物ごとの特殊能力をどう表現するか」という同じ問いに対して、それぞれの言語で
自然な答えが違います。

| | その言語で自然な形 | 何が手に入るか |
|---|---|---|
| TypeScript | interface と登録表 | 6匹目を追加するとき、既存のファイルを1行も触らずに済む（拡張に開く） |
| Python | 閉じた union と `match` | 対応を書き忘れたら、実行する前に検出される（網羅性を保証する） |

どちらが正しいかではなく、**何と何を交換しているのか**を見極めることが、
2本立ての目的です。同じ問いへの2つの答えを並べて置いてあるので、
片方だけを読んでも、もう片方と比べても読めます。

## 共通の設計

言語を問わず、この2本が共有している判断です。個別の理由と実装は各版の README にあります。

### 依存の向きを一方向に固定する

ゲームのルールを表す層は、画面にも実時間にも通信にも依存しません。依存は必ず
一方向に流れ、逆流させません。層の名前と数は言語ごとに違いますが、
**ルールの層がいちばん下にあり、何にも依存しない**という点は共通です。

### 境界を「約束」ではなく、検査で落ちる仕組みにする

「ルールの層でブラウザ API を呼ばない」を人が気をつけて守る形にはしません。
TypeScript では型定義を外すことで、Python では import を静的に禁止することで、
違反したらその場でエラーになるようにします。

### 同じ入力なら必ず同じ結果になるようにする（決定性）

乱数を「ゲームの結果に影響するもの」と「見た目だけのもの」に分け、
時間の進みを固定間隔（1/60秒）に統一します。`Simulation.step()` に
経過時間を渡さないのが、この判断の目に見える形です。

決定性の見返りは、あとから3つまとめて手に入ります。

- リプレイ（入力列を保存するだけで再現できる）
- 通信対戦（盤面ではなく入力だけを送れば同期する）
- バランス検証（画面を描かずに大量の試合を高速で回せる）

### 入力の出どころを1つの窓口にまとめる

人間のキーボード操作も、CPU の判断も、通信で届いた操作も、すべて
「行動の意思（Intent）」という同じ形にしてからゲーム本体に渡します。
ゲーム本体は、その意思が誰から来たのかを知りません。

この窓口があると、将来 CPU の中身をルールベースから機械学習や強化学習に
差し替えるときにも、ゲーム本体を変更せずに済みます。学習に必要な
「画面を描かずに高速で試合を回す」「同じ状況を再現する」も、決定性から自動的に付いてきます。

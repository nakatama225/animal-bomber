## LAN対戦（v3.0.0 に向けて・Phase 5 まで完了）

ホスト1台だけがシミュレーションし、ゲストは入力を送って結果を描くだけ（ホスト権威）。
**このゲームは決定論的でない**ので、同じ入力から同じ結果を再現する方式は採れない
（`Math.random` が43箇所・`dt` が可変・倍速スライダーが `dt` に直接乗る）。

### エンコーダは「送らないものを挙げる」形にしてある

`NET_SKIP` に載っていないフィールドは **既定で全部送る**。

⛔ 逆（送るものを列挙する形）にしない。列挙制だと、あとで `makePlayer` に
フィールドを足したときエンコーダが黙って落とし、ゲスト側だけ古い値を描き続ける。
原因が「通信のバグ」に見えて実体は「列挙漏れ」なので追いにくい。

実際、設計時に列挙していたフィールドは実物より少なかった。2026-08-17 に
`test/probe-keys.js` で計測したところ **`players` は46フィールド**あり、
`chargeCarry` / `chargeDir` / `digging` / `tongue` / `lastHitBy` / `lastMoveAt` /
`autoTimer` / `chickenCharges` は `makePlayer` に無く後から生える。
**宣言のコメントも古い**（`slimes` の宣言に `squash` が無いが実際には使っている）。
→ フィールドを調べる時は宣言ではなく `probe-keys.js` を走らせる。

### 送らないと決めたものと理由

| | 理由 |
|---|---|
| `players.controls` | `CONTROLS` への参照。直列化できず、ゲストは誰の操作も担当しない |
| `players.ai` | CPU の思考用。ゲストは思考しない |
| `players.animal` | ★別扱い。key だけ送って `ANIMALS[key]` に**参照で**繋ぎ直す。コピーを持たせると `getPower` が読む `powerBonus` の実体がホストと別になる |
| `bombs.ignore` | **`Set` は `JSON.stringify` すると `{}` になる**（エラーも警告も出ない）。読むのは `isSolidFor`/`canPlaceBomb`/`updateBombs`/`nextToBomb` だけで全部 `update()` の中。ゲストは `update()` を呼ばないので不要 |
| `G.speed` | 各自のローカル設定。ネット中は同期させない |
| `G.frame` / `G.lastDeaths` / `G.lastDeathFrame` | `update()` の中でしか読まない |
| `pits` の座標 | `drawPits()` は何も描かない。`renderCards` が「その人が仕掛けた数」を数えるので `owner` だけ送る |

⛔ `hp` を整数に丸めない。`CHARGE_ARMOR=0.5` の半ハートがあり `heartsOf()` が `>=0.25` で分岐する。
座標だけ小数第2位に丸める（素の `cx` は `1.4166666666666667` と書き出されるので3割減る）。

### ⚠️ `G.phase` は1つの名前に意味が2つ乗っている

`showScreen()` が画面名（`title`/`pick`/`rules`/`manual`/`play`）を書き、
ラウンド処理が `play`/`roundEnd`/`over` を書く。値は衝突しないが、
デコーダが無条件に上書きすると **まだロビーに居るゲストへ `roundEnd` が飛んで画面が消える**。
→ ゲストが既に試合画面に居るときだけ受け入れる。それまではロビーが持ち主。
「ゲストの画面が真っ白」はネットコードのバグに見えて実体はこれ、という類。

### 実測（`test/net.js`・2026-08-17）

4人・おに CPU で 600フレーム往復して **平均 3.2〜4.0KB/frame・60Hz で 186〜233KB/s**。
設計時の見積り（平均1,984B・116KB/s）より大きい。除外制にしてフィールドを
落とさなくしたぶん増えている。LAN なら問題ない量だが、**この数字は測り直したもの**なので
設計時の値を引用しないこと。

## Python 中継サーバ（Phase 3 完了・`games/server/`）

静的配信（HTML）と WebSocket 中継を**同一ポート**で受ける。ゲストはURLを1つ開くだけ。
ロビー無し・2人固定（番号の取り決めはまだ無い。繋いだ順にプレイヤー0=ホスト・プレイヤー1=ゲスト）。

### 構成

```
server/
  pyproject.toml         uv・websockets>=13・pytest/ruff は dev
  src/animal_bomber_server/
    netinfo.py    .local ホスト名 と LAN IP（両方候補として出す。片方が Wi-Fi 隔離で死ぬため）
    relay.py      Room クラス（プレイヤー番号の割り当て・転送・切断処理。中身を一切パースしない）
    http.py       process_request フックで HTTP GET を静的配信（WS昇格は素通り）
    main.py       起動・URL表示
  tests/          29件（relay 11・http 6・integration 8・netinfo 4）
```

### `Room` を「無知」に保った設計

中継が転送するメッセージ（盤面スナップショット・入力）の中身を一切パースしない。
知っているのは「どの接続が何番のプレイヤーか」だけ。パースし始めた瞬間、ゲームのルールを
知っているプログラムが2つになり、片方だけ仕様を変えると不整合の原因が
「サーバのバグ」に見えて実体は「仕様の言い忘れ」になる。

制御メッセージ（`welcome`/`peer_left`）だけは `Room` 自身が JSON で発行する。
これは中身の理解ではなく「誰が繋がっているか」の伝達なので無知の原則に反しない。

### ⚠️ ホスト切断は「試合終了」を中継レベルで保証する

ホストが抜けたら残り全員に `peer_left` を送ってから**中継側で全員の接続を閉じる**。
ホスト権威の設計上、ホストが落ちたら誰も盤面を進められないため、
「繋がってはいるが誰も何もできない」半端な状態を作らない。

### websockets 17 の実測（推測で書かない）

`serve()` の `process_request` は `(connection, request) -> Response | None`。
`None` を返すと WS ハンドシェイクへ進む。判定は `request.headers.get("Upgrade")`。
`Response(status_code, reason_phrase, Headers(), body)` で直接 HTTP 応答を組める。

```sh

```

29件緑。`test_integration.py` は本物の `websockets.serve` を OS 自動採番ポートで立てて

## Phase 4：ロビー画面・3〜4人・実配線（完了）

`setupPlayers()` に `if (CFG.mode==='lan') return setupPlayersLan();` の early-return を追加。
`setupPlayersLan()` は独立関数として新設（既存の1p/2p/vs分岐は無変更）——4枠固定で
先頭 `CFG.lanHumans` 人が人間、残りCPU。人間枠は全員 `CONTROLS.solo`
（LANは1台1人なので衝突しない。⛔ `CONTROLS.p3/p4` は追加しない）。

### 新規2画面：`lanScr`（たてる/参加する）・`lobbyScr`（プレイヤー一覧・動物選択・CPU設定）

**「たてる」も「さんかする」も中身は同じ接続処理。** この画面を開けている時点で
そのブラウザは既にホストのサーバから HTML をダウンロード済み（サーバはもう動いている）。
番号は空いている順に埋まるだけなので、クリック側の「意図」で処理を分ける必要が無い。
実際の役割（ホスト/ゲスト）は**サーバの `welcome` だけが決める**。

**ロビーの設定編集はホストだけ。** ゲストが自分のCFGを書き換えても `begin` 受信時に
ホストの cfg で `Object.assign` され上書きされるだけなので、編集させると
「選んだのに反映されない」体験になる。ゲストは見るだけ。

### `NET.handleMessage()` が全メッセージ種別のディスパッチャ

`welcome`（役割・プレイヤー番号・roster確定）／`peer_joined`（ロビー再描画）／`peer_left`
（ゲスト切断→CPU引き継ぎ or ホスト切断→タイトルへ）／`input`（ホストがプレイヤー番号で受信先を特定）／
`snap`（ゲストが`NET.apply`）／`begin`（ゲストが`CFG`反映＋`startGame()`）。

⚠️ **中継は1本のwsに複数ゲスト分の入力が来るので、送り主を明記する必要がある**。
`Room`は無知（中身を見ない）ため、`buildInput()`に `seat:NET.seat` を含めた
（`t:'input'` も追加）。ホストは `msg.seat` で対象プレイヤーを引く。

### ✅ ロビーでルールを決める（v4.2.0 で実装）

**v4.1.0 まで、ロビーで設定できるのは 人数・キャラ・CPU の強さ だけだった。**
体力・何勝先取・制限時間・サドンデスは「ルールをきめる」画面にしかなく、
**LAN のフローはその画面を1度も通らない**（タイトル → LAN対戦 → ロビー → はじめる）。
作者の言葉「LAN対戦のロビー、キャラしか選べないよね？なんで準拠してないんだ？」。
設計時のロビー仕様が「URL・参加者一覧・動物選択・CPU設定」だったところに、
ルール系が最初から入っていなかった。

v4.2.0 で足したもの：

| グループ | 中身 | 置き場所 |
|---|---|---|
| `hp0`〜`hp3` | 各枠の体力（1〜6回） | **その枠のキャラ・CPU強さの直下** |
| `wins` | 何勝先取（3/5/7/9） | ロビーの末尾 |
| `time` | じかん（1:00 / 3:00 / 5:00 / 7:00） | 同上 |
| `sd` | サドンデス ON/OFF | 同上 |

⭐ **体力を「枠ごと」に置いた理由**（作者の指定 2026-09-20）。上下＝グループ移動なので、
種類ごとにまとめると「1P の体力」を見るのに画面を目で往復することになる。
`MENU_ORDER.lobby` は `['humans','pick0','cpu0','hp0','pick1',…,'wins','time','sd','nav']`。

⭐ **選択肢は「ルールをきめる」画面と同じ刻みに揃える。** 同じものが2画面で違う刻みだと、
どちらが効いているのか分からなくなる。

### ⛔ `chips` の `set` がビルダーを組み直したら、自己再構築を止める（v4.2.0 で修正）

`chips()` は `set(v)` を呼んだ**あとに自分自身を作り直す**。だから `set` の中で
ビルダー全体を組み直すと、戻ってきた `chips` が**もう画面から切り離された古い箱**に
名簿を登録し直す（`buildLobby` の頭の `wrap.innerHTML=''` で親から切れている）。
症状は **「人数のチップにカーソルを置くと白い枠が見えなくなる」**
（カーソルは乗るのに、その要素は画面に無い）。

体力・勝利数・じかん・サドンデスは枠の数を変えないので、`set` は
`CFG` を書いて `NET.sendLobby()` を呼ぶだけにしてある。
**人数（`humans`）だけは `buildLobby()` を呼ばざるを得ない**（枠の数が変わる）。

**直し方**：`chips` の `onclick` で、`set` のあとに **`host.isConnected === false`
なら作り直さない**。

```js
set(o.v);
if (host.isConnected === false) return;   // 箱が画面から切られていたら作り直さない
chips(host,opts,get,set,screen,group);
```

⛔ **「組み直した set は true を返す」という約束にしてはいけない。** 最初そう実装して、
**「ルールをきめる」のサドンデスが壊れた**。`v=>CFG.sudden=v` は代入式なので
**v をそのまま返す**。ON を押した瞬間に約束へ引っかかって作り直しが止まり、
値は入るのに `.on` の印が OFF に残る。**約束ではなく、箱が切れているかという現実を見る。**

⚠️ `=== false` で比べるのは、`isConnected` を持たない環境（net.js の DOM スタブ）で
素通りさせるため。

⭐ **ハーネスの DOM スタブに `isConnected` を足した**（`unit.js`）。
`innerHTML=''` で子を再帰的に `_det=true` にするだけ。既存238件に影響ゼロで、
**このバグがテストで捕まるようになった**。DOM の付け替えはテストで検出できない、
という従来の線引きが1つ後退した。

### ✅ 3P と 4P の体力スロット（v4.2.0 で修正）

v4.1.0 まで、`makePlayer` のスロット判定は **`'2P'` かどうかの文字列比較1本**だった：

```js
const slot = o.isCPU ? 'cpu' : (o.label==='2P' ? 'p2' : 'p1');
```

`setupPlayersLan` は人間枠に `1P` `2P` `3P` `4P` を振るので、**プレイヤー2と3は
`'2P'` ではない＝`p1` に落ちる**。プレイヤー0・2・3 が `CFG.hpP1` を共有し、
3人以上でハンデ調整ができなかった。

**直し方**：`CFG.lanHp:[1,1,1,1]` を新設し、`makePlayer` が `o.hpSlot` を受け付けるようにして、
`setupPlayersLan` が `hpSlot:'lan'+i` を渡す。`baseHpOf` が `'lan0'`〜`'lan3'` を
`CFG.lanHp[i]` に読み替える。

⭐ **`p.maxHp` に焼き込まないのが要点。** `resetPlayersForRound` がラウンドの頭で
`baseHpOf(p.hpSlot)` を**引き直す**ので、`makePlayer` だけ直すと
**1ラウンド目だけ正しくて2ラウンド目から 1P の値に戻る**。
「最初は効いていたのに途中から違う」がいちばん追いにくい。テストを2本置いた
（枠ごとに独立／ラウンドをまたいでも保たれる）。

⭐ **既存の3変数（`hpP1`/`hpP2`/`hpCPU`）は 1p/2p/vs 用にそのまま残した。**
4枠の配列に作り替えると「ルールをきめる」画面（`buildHpRows`）と `setupPlayers` に波及し、
「1p/2p/vs が同一の `setupPlayers` を通る」ことを保証している既存テストが崩れる。

⚠️ **新しいフィールドを1つも足していない**（`hpSlot` は既存で、値の種類が増えただけ）。
`net.js` のエンコーダキー監査は「送っているキーの集合」を見るので、
プレイヤーに項目を足すとそちらが落ちる。

### ⭐ 回避策（v4.2.0 より前。もう要らないが記録として残す）

**ホスト権威なので、盤面を作るのはホストの `CFG`。** だから LAN に入る前に
別モードで `CFG` を書き換えておけば、そのまま試合に効いた。

1. ホスト側で タイトル → 1人vsCPU → キャラをえらぶ → ルールをきめる → 体力を上げる
2. もどる でタイトルへ（`CFG` はグローバルなので値が残る）
3. LAN対戦 → ロビー → はじめる

家族から「体力を増やしたい」と要望が出た日に、これで通した。
⚠️ この手順が「プレイヤー 0・2・3 に効く」のは、上の体力スロットのバグの裏返しだった。

### ⭐ ロビーの設定をゲストへ配る（`t:'lobby'`・v4.2.0）

ホストが設定を変えるたびに、今の値を全ゲストへ配る。**中継（`server/relay.py` の
`Room.route`）は中身を一切見ずに「ホストからのものは全ゲストへ」流すだけなので、
サーバ側の変更は1行も要らない** ——中継を無知に作ったことの見返りがここで出る。

```js
NET.sendLobby()   // ホスト → { t:'lobby', lanHumans, lanPicks, lanHp, cpuLevel, wins, time, sudden }
```

⛔ **`lanLocal` も `mode` も載せない。** `lanLocal` は `begin` と同じ理由（全ゲストが
「自分はプレイヤー0」だと誤解する）。`mode` は、ゲストの `CFG.mode` が `'lan'` になるのは
`begin` を受けたときだけ、という現状の切り分けを崩さないため。

⛔ **受信側は `Object.assign(CFG, msg)` にしない。** `t` が混ざるし、将来ホスト側が

**受け取るものを名指しで列挙**して、増えるときは必ずそこを触らせる。

⭐ **配るのは `buildLobby()` の末尾**（ホストのみ）。設定を変えた瞬間だけ送ると、
あとから参加した人には何も届かない（ロビーは待ち合わせ場所なので、参加は必ず後から来る）。
`peer_joined`／`peer_left` も `buildLobby` を通るので、末尾で毎回配り直せば拾える。
ゲスト側では `sendLobby` が早期 return するので往復しない。

⛔ **ゲスト側は `chips()` を使わない。** `screen` を渡さなければ名簿には載らないが、
**クリックでローカルの `CFG` が動いてしまう**。ホストの cfg で上書きされるので
「選んだのに反映されない」体験になる。ただのテキスト行にすれば「触れない」ことが
構造で決まる。テストで「ゲストのロビーは `MENU.list()` が空」をピン留めしてある。


**ラベル4つを `space-between` で等間隔に並べているのに、値は 0.5〜3 の線形。**

| ラベル | 表示されていた位置 | その位置の実際の値 |
|---|---|---|
| `0.5×` | 0% | 0.5 ✅ |
| `1×` | 33.3% | **1.33** ⛔ |
| `2×` | 66.7% | **2.17** ⛔ |
| `3×` | 100% | 3 ✅ |

```
W/2 + p*(100% - W)      ※ W = つまみの幅
```

⭐ **`W` は CSS に明示されている**（`::-webkit-slider-thumb{width:17px}`）ので、
ブラウザ依存で詰まらずに済んだ。1× は p=0.2 → `calc(20% + 5.1px)`、
2× は p=0.6 → `calc(60% - 1.7px)`。
両端（0.5×/3×）は元から 0%/100% なので、はみ出さないよう端揃え（`left:0` / `right:0`）。

⚠️ Firefox は `::-moz-range-thumb{width:15px}` で 2px ずれる。Mac のブラウザで遊ぶ前提なので
webkit の値で合わせた。⛔ **テストで守れない。実機で見る項目。**

### 家族と初めて2台で繋いだ日に出た2件（2026-08-22）

#### 1. ホストだけ「1人＋CPU3」になり、ゲストからはその1人プレイが見える

`NET.beginAsHost()` が `cfg` を**ゲストに送るだけ**で、自分の `CFG` に適用していなかった。
ホストの `CFG.mode` は既定の `'1p'` のままなので `setupPlayers()` が LAN 分岐に入らない。
ゲストは `Object.assign(CFG, msg.cfg)` するので正しく LAN モードになり、
ホストの1人プレイを忠実に描画する——**通信が完璧に動いているせいで、
原因がネットワーク側に見える**のが厄介だった。

修正は `Object.assign(CFG, cfg)` の1行。プランには「ホストが交渉済み設定を
**自分の CFG に書いてから**送る」と明記されていたので、実装時の抜け。

⚠️ **なぜ既存テストで捕まらなかったか**：`net.js` の begin 関連テストが
「`beginAsHost()` の中身をそのまま再現する」書き方をしていた。
**実装をコピーしたテストは、実装側の抜けを構造的に検出できない。**
テストを `NET.beginAsHost()` を実際に呼ぶ形で追加し、修正を戻すと
その1件だけが `expected lan, got 1p` で落ちることを対照実験で確認済み。

#### 2. 「たてる」を押したのにゲストになる（設計の不整合）

`lanHost` と `lanJoin` が同じ `joinLan` を呼び、役割はサーバの先着順で決まっていた。
UI が役割を選ばせておいて、その選択を捨てていた状態。家族が先にブラウザを開くと
サーバを立てた本人がゲストになる。

**採った解**：ホストの0番（プレイヤー0）を、サーバを動かしているマシンからの接続のために
**空けて待つ**（`Room(reserve_host_seat=True)`）。判定は `from_same_machine()` で、
接続の送信元 IP と宛先 IP を比べるだけ——`127.0.0.1` で開いても自分の LAN
アドレスで開いても一致し、よその端末だけが食い違う。

- **「優先」では足りない**。先によその端末が0番を取れば、元の混乱がそのまま戻る。
  だから予約制にした（この違いはテストで固定してある）
- `Room` は「なぜ優先されるのか」を知らない。`prefer_host` という抽象だけを受け取り、
  IP の判定は `main.py` が持つ（中継の無知の原則）
- ⚠️ **帰結**：サーバを動かしている Mac でブラウザを開かない限り、誰もホストにならず
  試合を開始できない。よそだけだとプレイヤー1〜3の3人までしか入れない。
  サーバ持ちが必ず参加する前提の割り切り。家族だけで遊ぶならその Mac 側でサーバを立てる

#### 3. 誰も接続していない人間枠が、ホストのキーボードで一緒に動く（分身）

**1 を直したことで初めて到達するようになった経路。** それまではホストが
LAN モードに入らなかったので死んでいた。

`setupPlayersLan()` は `i < CFG.lanHumans` の枠を全部 `isCPU:false` +
`controls: CONTROLS.solo` にする。誰も繋いでいない枠には `p.net` が付かない
（`receiveInput()` でしか付かない）ので、`inputOf()` がローカルのキーボードへ落ちる。
結果、ホストが右を押すと空き枠も一緒に右へ動く——**ラウンド中ずっと付いてくる分身**。

実測（`lanHumans=3`・プレイヤー0だけ接続・右を60フレーム）：

```
枠 | isCPU | p.net | 移動距離
0  | false | false | 3.085   ← 操作している本人
2  | false | false | 2.097   ← 誰もいないのに動く
3  | true  | false | 0.681   ← CPU（自律移動）
```

ロビーは空き枠を「⚪ 空き・待機中」と出すので、**「あとから入れるように多めに」と
人数を選ぶ操作で自然に踏む**。

**修正**：`beginAsHost()` で `lanHumans` を実際に接続している数まで切り詰める。

⛔ **「繋がっている人数」で切ると不十分**。プレイヤー1が抜けて2だけ残った穴あきのとき、
`roster.size` は2なので枠0・1が人間になり、空き枠の1で分身が復活する。
**先頭から連続して埋まっている数**で切るのが正しい。

⛔ **`setupPlayersLan()` に `NET.roster` を見せる形にはしない**。
プランの「`startGame()` は CFG だけを見て動く（テストとシミュレータが直接叩くため）」
に反するし、既存テストが全部この前提で書かれている。接続状態は
`beginAsHost()` で CFG に落とし込む——境界はそこ。

#### ⛔ テストを末尾に追記すると実行されない

`net.js` は最後に集計を出して `process.exit()` する。その後ろに `t(...)` を書いても
**一度も走らない**。しかも「27 件書いたのに 25 passed」という形でしか気づけない
（エラーは出ない）。追記は集計ブロックより前へ入れる。
2026-08-22 に実際に踏み、テスト件数が増えないことから発覚した。

#### ⛔ HTML だけの修正なら `.app` の再ビルドは要らないが、Python を触ったら要る

`.app` は `sys._MEIPASS` を読むのでビルド時に焼き込まれた HTML を配信する。
HTML だけの修正なら `Contents/Resources/animal-bomber.html` を差し替えて
`codesign --force --deep -s -` し直せば済む（`Contents/Frameworks/` 側は
Resources へのシンボリックリンクなので触らなくてよい）。
Python を変えたときは PyInstaller からやり直す。

**⛔ `uv run` でソースから起動して代用しようとすると Firewall で詰まる。**
`.app` は「接続を許可」で登録済みだが `python3.x` は未登録なので、
ループバック（127.0.0.1）だけ通り、LAN アドレス経由が無言でタイムアウトする。
症状が「サーバは動いているのに他端末から見えない」になって紛らわしい。

  リサイズにも追従。**マス数は変えないのでゲームバランスに影響しない**。
  1280×800→TILE40 / 1900×1000→**TILE51** / 2560×1440→TILE75（2026-08-06 まで固定33だった）
- 外周に葱ボン用レーン（幅 0.62タイル ≒ 20.5px。1マス丸ごとだと余白が目立つので細くした）
- **先取 3 / 5 / 7 / 9 勝**（デフォルト3勝）。1ラウンド勝つと★1つ。ラウンド間でパワーアップはリセット、★は持ち越し
- 制限時間 **1 / 3 / 5 / 7分**（デフォルト3分）。選択肢を変える時は `CFG` の既定値が候補に入ってるか確認する
  （入ってないと、開いた時にどれも選ばれてない見た目になる。テストで見張ってる）
- **サドンデス**（ON/OFF）: 時間切れで複数生存 or 全員同時死 → ソフトブロック全消し・全員HP1・
  **💣8・🔥8・👟6 全部MAX**・60秒延長。1回だけ
  - 全部MAXは 2026-08-04（それまで初期値に戻していた）。**サドンデスの半分がひきわけで
    ラウンドを空転させていた**のが理由。👟は最初「初期値のまま」指示だったが同日にMAXへ変更
- **爆風にたえる回数（HP）は 1P / 2P / CPU で別々に設定**（各1〜6）。デフォルト全部1
### CPU の作り（強化学習でもALifeでもない）

**ルールベース**。学習は一切していない。パラメータは人力で決めて `probe-cpu-strength.js` で
対戦させ、数字を見て詰める（人力のチューニングループ）。

1. **危険地図** `dangerMap()` — 各マスが「あと何秒で燃えるか」。**誘爆を伝播**させる。
   同一フレーム内はキャッシュ（CPU の全判断の土台なので作り直さない）
2. **状態機械** `planCPU()` — 上から順に当てはまった1つを採る：
   `dodge`（葱の射線から外れる）→ `flee`（危険マスから逃げる）→ `attack`（射線の敵に置く）
   → `item`（アイテムを拾う）→ `hunt`（敵に近づく）→ `dig`（ソフトブロックを壊す）→ `wander`
3. **経路探索** `bfsPath()` — 幅優先。`avoid`（危険マス）と `dodgeBad`（ハズレアイテム）で通行を制限
4. **置く前の安全確認** `canEscapeAfterBomb()` — 置いた前提の危険地図を作り、逃げ切れる経路があるか
5. **強さのツマミ** `CPU_LEVELS` — 下記

### CPU の自爆を潰した記録（2026-08-08・`probe-cpu-strength.js`）

作者「つよいでもたまに自爆して死ぬ」→ 実測すると**たまにではなく死因のほぼ全部**だった。

| | 自爆率（被弾のうち自分の爆風） | 相手との最接近 |
|---|---|---|
| 修正前 つよい | **100%**（11/11） | 18〜20マス（届いてない） |
| 修正前 ふつう | **100%**（12/12） | 16〜19マス |
| 修正後 つよい | 25〜50% | **0〜1マス** |
| 修正後 おに | 0〜27% | **0〜2マス** |

**原因は3つあった。全部別のバグ**。

1. **逃げ先が爆風の中だった**。`nearestSafePath` の候補2が「今より猶予が長いマス」で、
   そこは**まだ爆風の中**。着いて止まった瞬間に死ぬ。
   → `escape>=1` の CPU は「完全に安全なマス」しか目標にしない。見つからなければ動かない
2. **`dangerMap` が誘爆を読めてなかった**。爆弾Aの爆風が爆弾Bに届けば B は A のタイマーで爆発するが、
   B 自身のタイマーで塗っていた。CPU は「まだ2秒ある」と誤読して置いた場所で死ぬ
   → 誘爆連鎖を反復で伝播させた
3. **ハズレアイテムを踏んで動けないまま自爆**。たまねぎ3秒・うんこで固まってる間に自分の爆弾が爆発。
   軌跡を追ったら**1.5秒間まったく動いていなかった**
   → `bfsPath` に `dodgeBad` を足し、「避けて探す→無ければ避けずに探す」の2段で使う

あわせて **狭い所で置き続けて自分を追い詰める**のも直した（`live`＝同時に生かす爆弾の数、
`room`＝袋小路では置かない）。

### CPU の往復（2026-08-08・2回目）

きつねが「いったりきたりしかしない」との報告。実測：

| | 訪れたマス | 置いた爆弾 | 1マス往復 | 逃走判定 |
|---|---|---|---|---|
| きつね 修正前 | 39 | 25本 | **106回** | 116回中 通ったの15回 |
| きつね 修正後 | 20 | 16本 | **23回** | **15回**中 15回 |
| かえる 修正前 | 26 | 16本 | **147回** | 148回中 22回 |
| かえる 修正後 | 8 | 4本 | 13回 | 4回中 4回 |

原因は **「置けない」と判定した直後に `a.think=0` で即座に狙い直し、また同じ場所を狙う**振動。
判定回数が116回もあるのに通るのは15回だけ、という数字がそれを示していた。

→ `a.bombBan`（0.8秒）を入れて、置けなかった直後は
**爆弾を狙う行動（attack / dig）そのものを飛ばす**（アイテム拾い・敵に近づく・うろつきに回す）。
`dig` も飛ばすのが要点。目標へ向かっても置けないなら、着いた所で止まって往復するだけ。

### ⛔ 「袋小路では爆弾を置かない」は入れてはいけない（2026-08-08・3回目）

自爆対策として `room`（隣接の通れるマスが2方向以上ないと置かない）を入れたら、
**つよい／おに が40秒で爆弾0本**になり、うろつくだけになった（うさぎ 訪れたマス5・wander 30秒）。

ボンバーマンは**ブロックを壊して道を作る**ゲームなので、序盤は必ず袋小路。
「道が狭いから置かない → 壊せない → ずっと狭い」で永久に抜け出せない。**撤去した。復活させない**。

手がかりは `probe-fox-cpu.js` の「**逃走可 33/33（全部通ってる）なのに爆弾0本**」。
`canEscapeAfterBomb` は通っていて、その後の自前チェックで弾いていた。

あわせて `live`（同時に生かす爆弾数）超過は **`bombBan` を立てない**ようにした。
`live` は「場所が悪い」のではなく「今は待つ」だけなので、狙いを変える必要がない。
`bombBan` は `canEscapeAfterBomb` が false の時だけ立てる。

⚠️ 火力13にした副作用で、**置ける場所そのものが減っている**（爆風が十字に13マス伸びるので
4マス以内に安全マスが無いことが多い）。往復はこれが引き金だった。

**追跡距離**：盤面 23×17 の対角は約36マス。旧 `22*aggro` では届かず、相手の陣地に着く前に終わっていた。
`hunt` を絶対値にした（よわい14／ふつう26／つよい36／おに99）。

⚠️ **おには「つよいより明確に強い」までは行っていない**（6マッチで 8-18〜13-10 と揺れる）。
ふつうには 18-0〜18-5 で圧勝する。さらに上げるには「相手の逃げ道を塞ぐ配置」「先読み」など
今のルールベースの外側が必要。

- **CPU のとくぎ判定は「歩ける経路の距離」で見る**（`foePathDist`）。
  マンハッタン距離だと、ブロックで隔てられた相手を「近い」と誤判定して無駄撃ちする
  （きつねが壁越しに狐火を消費した報告の原因・2026-08-06）。
  狐火＝経路7マス以内／ポロポロ＝5マス以内／落とし穴＝12マス以内で仕掛ける
- **とくぎの抽選は毎フレーム引かない**（`a.skillCool`）。60回/秒で引くと `skillUse` 0.25 でも
  実質100%になってしまい、強さ設定が効かない。外れたら0.4秒待つ
- **CPU の強さは1体ずつ設定**（`CFG.cpuLevel[0..2]` / `CPU_LEVELS`）。よわい／ふつう／つよい／おに。
  デフォルトは**ふつう**。ツマミ：
  `think`（判断間隔）／`sloppy`（危険の見落とし率）／`aggro`（攻める度合い）／
  `skillUse`（とくぎを使う確率）／`escape`（1.0 なら完全に安全なマスしか目標にしない）／
  `sharp`（危険な時だけ判断間隔を 0.03 に詰める）／`hunt`（追跡距離・マス）／`item`（アイテム探索距離）／
  `live`（同時に生かす自分の爆弾の数）／`room`（袋小路では置かない）／
  `greedy`（火力・爆弾を優先して集める）／`ruthless`（射線の敵は必ず狙う）
  **命中精度そのものは触らない**（触ると自滅するだけで弱くならない）。
  ⚠️ `live` の最適値は `room` 撤去で変わった。現在 よわい1／ふつう2／つよい3／おに4。
  `room`（袋小路では置かない）は**撤去済み。復活させない**（上記）
- モード: 1人vsCPU×3 / 2人vsCPU×2 / 2人タイマン
- **ゲーム速度 0.5〜3倍のツマミ**（サイドパネル。サブステップで回すので当たり判定は飛ばない）
- **やり直し機能は無い**（R キーごと削除。操作ミスで暴発してラウンドが際限なく進む事故があった）

| | 粒度 | このゲームでの例 |
|---|---|---|
| MAJOR | 遊ぶ側が「別のゲームになった」と感じる規模。**年に1回あるかないか** | 画面フロー全面改装（起動手順が別物になった）＝2.0.0 ／ **LAN対戦＝3.0.0（1台のゲームが2台のゲームになった）** ／ **ゲームパッド対応＝4.0.0（キーボードの前に座る遊びでなくなった）** |
| MINOR | 機能・キャラ能力・画面を**足した**（後方互換） | 新とくぎ・新モード・CPU強さ設定・先取制 ／ **メニューのカーソル＝4.1.0** ／ **ロビーでルールを決める＝4.2.0** ／ **バトル中にコントローラーで設定へ＝4.3.0** |
| PATCH | バグ修正・数値調整 | 当たり判定・もぐらの詰み・Space暴発・きつねCPU往復・突進のアイテム事故 |

**操作キーが変わった程度は MAJOR ではない**（MINOR か PATCH）。

⚠️ **ただし「入力デバイスが増える」のは別。** キーの割り当て替え・増設は MINOR か PATCH だが、
**キーボード以外で遊べるようになる**のは遊び方そのものの変化なので MAJOR（＝4.0.0）。
判断の分かれ目は「**どのキーを押すか**」が変わったのか、「**何を持って遊ぶか**」が変わったのか。
2026-09-20 に作者が 4.0.0 を指定。この一文を足さずに番号だけ上げると、後から読んだ人が
上の行と矛盾すると判断して格下げしにくる（だから番号とルールを同時に直す）。

⚠️ **既存の技・アイテムの秒数／範囲／効きを変えるのは PATCH**。MINOR ではない。
2026-08-08 に2回 MINOR を付けて作者に指摘され、2回とも PATCH へ格下げした。判断はこの一言で足りる：

| 言い方 | |
|---|---|
| 「**〜ができるようになった**」（新しい技・モード・画面・選択肢） | MINOR |
| 「**〜を〇秒にした / 〜の効きを変えた / 説明を足した**」 | PATCH |
| 「**〜が直った**」 | PATCH |

内部に仕組み（例：動物ごとの長押し秒数を持たせる）を足しても、
**遊ぶ側から見て「調整」なら PATCH**。

⭐ **MINOR と PATCH を同時に積んだら MINOR。PATCH の桁は 0 に戻す。**
2026-09-24 に作者が確認（「MINORとパッチ両方あてたらMINORが優先？」）。semver の規則どおりで、
`4.2.1` に「機能追加1件＋バグ修正2件」を積んだら **`4.3.0`**。`4.3.1` にはしない
（`4.3.1` は「4.3.0 を出したあとにバグを直した」の意味になり、履歴の順序が嘘になる）。

### きつねの一列ドン設置（`plannedLineBombs`）

**足元ではなく「1マス前」から並べる**（作者の指示・2026-08-08。本家ルーイのイメージ）。
足元から置くと自分が列の先頭に埋まる。前から置けば後ろへ下がって逃げられる。

- **前が壁なら技ボタンでは置かない**。足元に置きたい時は**普通の爆弾ボタン**を使う（作者の指摘）。
  一度「前が壁なら足元に1本」というフォールバックを入れたが、それは要らない機構だった。
  CPU も同じで、一列が置けない時は `placeBomb`（1個置き）に切り替える

### CPU が狭い範囲を往復する（2026-08-08・4回目）

きつねが40秒で**訪れたマス3・往復5.1回/秒**（他は1.7〜2.9）。位置を1フレームずつ追って正体が分かった：

```
(1,2) dig  → 上を向いて (1,1) に置く   ← そこには壊せる物が何も無い
(1,3) flee → 爆風で押し戻される
(1,2) dig  → また (1,1) に置く …（40秒くり返す）
```

**同じマスに置き直して、自分の爆風で自分を押し戻していた**。
→ `a.lastBombAt` / `a.lastBombT` を持たせ、**同じマスには4.5秒 置き直さない**。

| | 訪れたマス | 往復/秒 |
|---|---|---|
| きつね 修正前 | 3 | 5.1 |
| きつね 修正後 | 5〜28 | 3.0〜4.0 |
| ふつうの全キャラ | 11〜45 | 0.7〜0.8 |

⚠️ **おに はまだ往復が多い**（きつね3.9 / ぞう4.0）。判断間隔が 0.05秒と短いぶん、
目標の切り替えが速すぎるのが原因と見ている。ふつう・つよいは実用範囲。

**測り方の注意**：`probe-fox-cpu.js` は**生存秒**も出す。
「訪れたマス」は生存時間に比例するので、早死にすると勝手に小さくなる。
一度これを見ずに「probe の測り方の問題」と誤診した。**必ず 生存秒 と 往復/秒 を並べて見る**。

### ゲームパッド（v4.0.0・2026-09-20）

実機は **STK-7043**（Switch 向けだが Xbox 互換モードあり）。実測の一次資料は
`gamepad-stk7043-mapping.md`、検出ページは `gamepad-probe.html`。
`mapping:"standard"` が出たので**製品固有の対応表を書かずに済んだ**（十字はボタン12-15・`index` は 1）。

**⭐ 方式：パッドの押下を合成キーコード（`'Pad:A'` 等）として `keys`/`pressed` に注入する。**
`hold()`/`edge()` が `inputOf()` と `NET.buildInput()` の**両方**から使われているので、
ここへ注げば 1人プレイも LAN対戦も同じ道を通る＝**ネットコードに一切手を入れずに済む**。
倍速サブステップの `pressed.clear()`（上の事故）もそのまま効く。
⛔ `inputOf()` にパッド分岐を足す方式は採らない。`NET.buildInput()` がそこを通らないので
**ゲストだけパッドが効かない**うえ、`pressed.clear()` の外側になって倍速の事故が再発する。

**⛔ 1台のMacに1人ぶん。** 追加したのは `CONTROLS.solo` だけ（`p1`/`p2` には足さない）。
1台に2個挿して2人は**やらない**（`makePlayer` の HP スロットが `o.label==='2P'` の文字列比較で
決まる等、4箇所の作り直しが要る。必要になったら別途）。

| ⛔ | なぜ |
|---|---|
| **`PAD.prev` を絶対にクリアしない** | エッジは「前回のポーリング状態」との差分だけで作る。`startRound()` が `keys.clear()` するので、`!keys.has(code)` で判定すると押しっぱなしのAが新しいエッジになり**初期位置で爆発**が復活する。「後始末」のつもりで `startRound`/`blur`/切断でクリアしても同じ。**クリアしないのが仕様**（パッドが消えれば `now` が空になって自己修復する） |
| **注入 → 画面遷移 の順序が仕様** | 逆にすると `advanceBanner()` → `startRound()` の `pressed.clear()` の**後**にAのエッジが入り、そのフレームの `update()` が爆弾として消費する |
| **2人プレイで無視するとき早期 return しない** | 注入だけを止めて `PAD.prev` は常に更新する。止めると 2p 中に離したボタンが prev に残り、1p へ戻ったとき①離したボタンが押しっぱなし扱い②押し直してもエッジが立たない |
| **ガードは `typeof globalThis.navigator?.getGamepads === 'function'`** | Node 26 には `navigator` が**存在する**（`getGamepads` だけ無い）ので `typeof navigator !== 'undefined'` では素通りする。しかも素の `navigator?.x` は未宣言環境で `?.` に到達した時点で throw する（`typeof` の ReferenceError 保護は素の識別子にしか効かない）。トップレベルで触ると**全テストが1件も走らずに落ち、エラーは「R1: location/WebSocket」という無関係な原因を名指しする** |
| **`getGamepads()[0]` に決め打ちしない** | 実機は **index 1** だった（Bluetooth の接続順で決まる）。`mapping==='standard'` の最初の1つを拾って `gp.index` をラッチする（試合中に別のパッドが目を覚ますと選択が静かに移る） |
| **離したコードを `keys` から抜く** | 省くと電池切れ／Bluetooth 切断の瞬間に最後の入力が残り、**壁に向かって歩き続けて操作不能**になる |
| **`act` に L2/R2 を入れない** | `hold(c.act)` は OR。`.pressed` が立つしきい値はブラウザ実装依存なので、トリガに指を乗せているだけで `actHold` が溜まって とくぎが暴発しうる。実機で `.pressed`/`.value` を測ってから足す（未測定） |
| **HOME は割り当て不能** | macOS がシステム側で握っていて Gamepad API に届かない（ショートカットを切っても、アプリが開かなくなるだけ） |
| **画面遷移のトリガに `pressed.has()` を使わない** | ポーリング内で立てたエッジだけを集めたローカルの `hit` を見る。`pressed` を見ると「`loop()` の末尾が毎フレーム掃除してくれる」前提に依存し、その前提は**ハーネスが `loop()` を呼ばないのでテストで守れない**。将来 loop の構造が変わると「Start 押しっぱなしでポーズが即解除される」形で静かに壊れる（`hit` にしたのでテストが書けるようになった） |
| **スティックは優勢な軸だけ採る** | 軸ごとに独立してしきい値を当てると、真上から30°倒しただけで `|x|=0.50 |y|=0.87` で両方が 0.5 を超え、`movePlayer` の水平優先で**必ず横に歩く**。全周の約33%が「押した向きと違う方向」になる＝「まっすぐ歩けない」。しきい値は入り 0.5／抜け 0.35（ヒステリシス。境界で手ブレすると `p.dir` がバタつき、爆弾の一列置き・鼻水・舌の向きが暴れる） |

**仕様変更（2026-09-20 作者承認）：ラウンド開始時に押していた技ボタンは、一度離すまで効かない**
（`resetPlayersForRound` で `p.actFired=true`）。キーボードは OS のリピート遅延（macOS 既定 ≈500ms）が
偶然の緩衝材になっていたが、パッドは次フレーム（16ms）で hold が戻る。
⚠️ **実害の出方が分かりにくい**：`doSpecial` は `p.chicken` を持っている時しか撃たず、
ラウンド頭で chicken は消えている。だから押しっぱなしにした直後は**空振りするだけで何も起きない**。
暴発するのは**そのまま走り回って 🍗 を拾った瞬間**。テストもそこを測っている。
⛔ サドンデス突入（`enterSuddenDeath`）側は `actFired=false` のまま。あちらはバナーを挟まない
試合中の連続した流れで、押下を捨てる理由が無い。

**同時に直した既存バグ2件**（パッドが実害を増やすため）：

1. `advanceBanner()` にゲストガードが無かった（`togglePause` にはあった）。
   ここ1箇所で keydown・`bAgain` ボタン・パッドの3経路を塞げる
2. **切断で試合が畳まれず、ゲストが毎フレーム TypeError を投げ続けていた。**
   `NET.ws.onclose` は `NET.role=null` にするだけで `raf` も画面も触らなかったので、
   次の `loop()` がゲスト分岐に入らず `update()` へ落ち、`p.controls` は `apply()` が
   null にしているので `hold(c.up)` でクラッシュし続ける（画面は最後のフレームで固まる）。
   → `onclose` から `backToSetup()` を呼ぶ。ホスト側も戻す（中継が死んだ時点で
   ホスト権威の試合は成立せず、`p.net` が最後の値のまま残ってその枠が歩き続けるため）。
   ⛔ **同時に `disconnect()` で `ws.onclose = null` にしてから閉じる。**
   外さないと、ロビーの「もどる」など**自分から切る経路**でも後始末が非同期に走り、
   その間に始めた1人プレイを raf ごと畳んでしまう。自分から切った場合の画面遷移は

### メニューのカーソル（v4.1.0・2026-09-20）

v4.0.0 は**ゲーム中の操作だけ**を対応させた。メニュー（タイトル／キャラをえらぶ／ルールをきめる／
マニュアル／LAN／ロビー／リザルト）はクリック専用のままで、**キーボードの矢印キーでも動かなかった**。
作者が実機で最初に踏んだのがこれ。v4.1.0 で全部カーソルに乗せた。

**⭐ 方式＝名簿（レジストリ）。画面を走査してボタンを探すのではなく、
ボタンを作る関数が、作った直後にその場で `MENU.add(画面, グループ, el, act)` する。**

| ⛔ | 理由 |
|---|---|
| **DOM を探しに行かない** | ①押した瞬間に消える（`chips`/`buildPickers`/`buildLobby` は `innerHTML=''` で丸ごと作り直す。ロビーは `peer_joined`/`peer_left` から本人の操作と無関係に呼ばれる）②ハーネスの `querySelectorAll` は常に `[]` を返すので「テストは緑なのに実機だけ動かない」になる ③動物カードは `<div>` で `tabindex` も無く、ブラウザ標準のフォーカス移動に最初から乗らない |
| **カーソルは (グループ, 項目) の2段** | 上下でグループ、左右でグループ内。座標で動かすと `.animals`/`.cols` の `auto-fit` で列数が窓幅により変わる（5列→4列→3列…）ため決まらない |
| **縦に並ぶボタンは1個ずつ別グループ** | 上下＝グループ移動なので、縦5個を1グループに入れると左右キーで縦の並びを辿ることになり操作が逆になる |
| **`className` を直に書く（`classList.add` を使わない）** | ハーネスの `classList` は完全な no-op で `contains` が常に false。既存のビルダーも `c.className='acard'+(...)` と直代入している。登録時の `base` に足す形にするので `.acard.on`（選んだ印）が消えない |
| **見た目は `outline` だけ** | `border-color` と `box-shadow` は `.acard.on` / `.chip.on` が使っている。上書きすると「どれを選んだか」が見えなくなる。`outline` はファイル全体で1箇所（速度スライダーの `outline:none`）しか使っていない空きチャネル |
| **`hit`（エッジ）は `active` ゲートの外で作る** | `active` は `CFG.mode` を見るので 2p/vs で偽になり、しかも `backToSetup` は `CFG.mode` を戻さない。内側で作ると「一度タイマンを選ぶとタイトルに戻ってもカーソルが死ぬ」 |
| **メニュー分岐は `if (!active) return` より前** | 同上 |
| **リザルト画面だけ「最初の一押しを飲み込む」を適用しない** | 他の画面では、枠が見えないまま A が入る事故を防ぐため1押し目を枠出しに使う。だがバナーは A＝次へ が唯一の主操作で初期位置もそこ。1回目を捨てると「A が効かない」になり、**事故#11 のテストが落ちる**（実際に落ちて気づいた） |
| **飲み込むのは A だけ。移動と B は通す** | 枠は `mousemove` のたびに消える仕様なので、マウスに少し触れたあとの一押しが毎回捨てられ「たまに効かない」になる |
| **`backToSetup` で `MENU.on=false` とダイアログを畳む** | 消さないと、試合を終えてタイトルに出た瞬間に触ってもいないのに枠が光る。ダイアログはホストが落ちた時（`ws.onclose`→`backToSetup`）の唯一の後始末 |

**駆動系**＝`menuTick()`（自己再登録の rAF）。中身は `if (!raf) pollGamepads();` の1行。
`raf` はゲームループが生きている間だけ非 null（`startRound` で立ち `backToSetup` で null）なので、
これがそのまま「二重ポーリング防止」になる。同じフレームで2回ポーリングすると
1回目がエッジを消費して2回目が空になり、ゲーム中の入力が1回おきに消える。

**キーボードの矢印キー**は `KEY_TO_PAD` でパッドのコードに翻訳して同じ入口へ流す。
操作の意味を決める場所を2つに増やさないため。

**確認ダイアログ**（`askConfirm`）：⛔ `confirm()` を使わない。OS のダイアログは
コントローラーで押せないので、「コントローラーだけで遊べる」はずが最後の1枚だけ
トラックパッドに手を伸ばす羽目になる。画面の中に出して、カーソルが乗る2択にする。
カーソルの初期位置は**「やめる」側**（危ない方を初期位置にしない）。
切断は経路を問わず全部 `askDisconnect` を通る（クリックでも B でも同じ確認が出る）。

**テスト 27本**（unit.js の13節）。逆向き確認で**テストが居ない箇所を2つ発見して埋めた**
（`chips` の `MENU.clear` を消しても緑のまま／`display:none` を飛ばさなくても緑のまま）。

### ⛔ `clamp` はビルダーの末尾でだけ走らせる（v4.2.0 で修正）

**症状**：ロビーでキャラを選ぶたびに、白い枠（コントローラーの現在地）が
**1P の左上のうさぎに戻る**。選んだキャラの黄色い印は正しく残るので、
「決定は効いているのにカーソルだけ飛ぶ」という見え方になる。
作者が実機で発見（2026-09-20）。

**真因**：`chips()` の末尾が `MENU.refresh()`（＝`clamp()` + `paint()`）だった。
`buildLobby()` は頭で全グループを空にしてから作り直すので、**最初の `chips` 呼び出しの
時点では名簿に `humans` と `nav` の2グループしか無い**。そこで `clamp` が走って
カーソルが丸められる。キャラカードはそのあと足されるが、丸められた値はもう戻らない。

| 順 | 起きること | そのときの名簿 |
|---|---|---|
| 1 | `buildLobby` の頭で全グループ `MENU.clear` | ほぼ空（`nav` だけ残る） |
| 2 | `chips(…,'lobby','humans')` | `humans` ＋ `nav` = **2グループ** |
| 3 | その末尾の `MENU.refresh()` → `clamp` | `gi=3` が範囲外 → **`gi=1`**、`ii=2` → **`ii=0`** |
| 4 | このあとキャラカードを `MENU.add` | 8グループに戻る |
| 5 | `buildLobby` 末尾の `refresh` | `gi=1, ii=0` は範囲内なので**もう戻らない** |

**直し方**：`chips()` の末尾を **`MENU.paint()` だけ**にする。`chips` 自身の作り直し
（chip を押した経路）は `opts` が同じで項目数が変わらないので、はみ出しの補正は要らない。

⛔ **そのかわり、`chips` を使うビルダーの末尾に `MENU.refresh()` を揃える。**
`buildSetup` / `buildHpRows` / `buildCpuRows` は `chips` の末尾の `refresh` に
**ただ乗りしていた**ので、そこを外すと丸め手が誰も居なくなる。
`buildLobby` / `buildPickers` は元から末尾に持っていた。

⭐ **`buildHpRows` / `buildCpuRows` は `showScreen` から単独で呼ばれる**
（`if (name==='rules'){ buildHpRows(); buildCpuRows(); }`）ので、
`buildSetup` 末尾の `refresh` にも `buildPickers` にも乗れない。**保険ではなく必須。**
⚠️ ただし `showScreen` は末尾で `MENU.reset()` するので、**画面遷移だけを試すと
いつでも緑になる**。テストはビルダーを直接呼ぶ形で書く。

⛔ **`buildHpRows` と `buildCpuRows` は1本ずつ試す。** まとめて呼ぶと、
`buildCpuRows` の早期 return（`if (!n){ MENU.refresh(); return; }`）が
両方の丸めを肩代わりして、**片方の `refresh` を消しても緑のまま通る**。
最初にそう書いて、逆向き確認で落ちないことに気づいた。

⭐ **この症状はキャラ選択に固有ではない。** `chips` を使うビルダー全部が同じ構造を
持っていた。ロビーに設定を足すほど `chips` の呼び出しが増えるので、
**ロビーの機能追加より先にこれを潰した**（そうしないと実機確認が通らない）。

### きつねCPU が戦闘に参加しない問題（2026-08-06、`probe-fox-cpu.js`）

原因は作者の見立てどおり **一列ドン置き × 置き場探索のバッティング**。
`canEscapeAfterBomb` が「満載で一列置いた前提」で判定するので、ソフトブロックだらけの序盤は
ほぼ必ず「逃げ切れない」になり、置けないまま同じ狙いを立て直して往復し続けていた。

| | 訪れたマス | 置いた爆弾 | 1マス往復 |
|---|---|---|---|
| 修正前 | 3 | **0本** | **190回** |
| 修正後 | 7 | 5本 | 10回 |

修正は **`canEscapeAfterBomb` を緩めない**（緩めると自滅する）。
`plannedLineBombs(p,tx,ty,cap)` に本数上限を足して、CPU が満載→1本まで降りながら
「逃げ切れる本数」を探し、`p.lineCap` で実際の設置本数を絞る。**人間は常に満載**。

### サドンデスで火力/爆弾MAXにした効果（2026-08-04、各9マッチ）

| | ひきわけ率 | サドンデス突入ラウンドのひきわけ率 | 平均決着 |
|---|---|---|---|
| ①MAX無し（旧） | 34%（13/38） | **50%**（13/26） | 1141s |
| ②💣🔥MAX・👟初期値 | 19%（10/53） | **28%**（10/36） | 978s |
| ③💣🔥👟 全部MAX | 14%（8/59） | **19%**（8/43） | 1083s |

サドンデスで **両者が同時に死ぬと勝者なし＝ひきわけ**。`G.suddenUsed` が立ってるので2度目の
サドンデスも来ず、ラウンドを1つ消費するだけで優勝に近づかない。これが「勝負つかない」の中身だった。
**サドンデスの発生数は指標にならない。見るのは ①ひきわけ率 ②優勝までのラウンド数**（sim.js が両方出す）。

残りのひきわけは同時死。**ゼロにはなってない**。もっと詰めるなら
「サドンデス中のひきわけは 再サドンデス」など `G.suddenUsed` 側の設計変更が必要（未着手・作者未承認）。

きつねの💣MAX懸念（8本ドン置き＋火力8で自滅しないか）は `probe-fox-sudden.js` で潰した：
盤面 23×17 の全マス×全方向 980通りすべてで逃走経路あり（うち400通りは満載8本）。
逃げ道は「後ろへ1マス＋列から外れる」。ただし**マスの真ん中まで入り切ること**
（境界に立つと BLAST_HITBOX が隣のマスに跨って被弾する。テストで1回踏んだ）。

## 進め方の作法（このPJで確立したもの）

- 承認済み設計から変えたら**必ず報告**して「戻していいなら戻す」と添える（作者が明示的に評価した）
- **「実装したら壊れそう」と思った時点で聞く**。数値だけ報告して実装を進めるのは足りない
  （うんこポロポロを 11×11＝120マスで作った時、note に「盤面の半分近く」と書きながら実装した。
  自覚があるなら実装前に確認する）

  ① うんこポロポロの範囲（「5マスの正方形」→ 距離5の11×11にした）
  ② 舌のペナルティ（「舌に爆風があたると」→「爆弾に触れたら35秒ロック」という別機構を新設）

- 一括の機械置換は**件数を突き合わせる**（テストを4件消し込んだ事故が1回）

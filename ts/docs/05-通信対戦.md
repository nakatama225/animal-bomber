# 通信対戦（ロックステップ）

段階9の主題は**窓口を差し替えるだけで通信対戦になること**の確認です。同じ LAN にいる
2〜4台で、1つの試合を遊べるようにしました。

## 盤面を送らず、操作だけを送る

原型の LAN 対戦は、ホストの1台だけが試合を進め、毎フレーム盤面を丸ごとゲストへ配っていました
（ホスト権威）。原型は乱数を43か所で1本のまま引いていて、同じ操作から同じ試合になる保証が
無かったためです。

この版は段階1から、同じ種と同じ操作からは必ず同じ試合になるように作ってあります。
そこで**全員が手元で同じ試合を進め、送り合うのは1 tick ぶんの操作だけ**にしました
（ロックステップ）。

| | 原型（ホスト権威） | この版（ロックステップ） |
|---|---|---|
| 試合を進める端末 | ホストだけ | 全員 |
| 送るもの | 盤面の全体を毎フレーム（4人で、受け取る量が1秒あたり 186〜233KB。原型のノートの実測） | 1 tick ぶんの操作（1通50バイトほど。4人で、受け取る量が1秒あたり 9KB ほど） |
| ホストが抜けたら | 試合を続けられない | 続けられる（抜けた人は CPU が引き継ぐ） |
| 端末ごとの違い | 起きない（盤面を上書きする） | 起きたら検出して止める |

## 窓口を差し替えただけ

段階1で `IntentSource` という操作の窓口を置き、段階4でキーボードとゲームパッドを、
段階6で CPU を、同じ窓口に繋ぎました。記録の再生も同じ資格で試合に繋がります。

通信対戦で足したのは、この窓口の実装1つ（`NetworkIntentSource`）です。
中継から届いた操作を tick ごとに流します。試合の側（`GameSession` と `Simulation`）には、
通信のための分岐を1つも足していません。

⭐ 自分の端末で操作しているプレイヤーも、この窓口を通します。自分の操作も相手と同じだけ
遅らせて使わないと、自分の手元でだけ先に動いて試合がずれます。

## 1 tick の進め方（`src/net/LockstepDriver.ts`）

1. tick T を進める前に、人間全員の tick T の操作が届いているかを見る。
   1人でも届いていなければ、進めずに待つ
2. 届いていれば、自分のキーボードを読んで **tick T+3 の操作**として送る
3. 全員の tick T の操作で、試合を1 tick 進める
4. 20 tick ごとに、状態の要約を中継へ送る

試合が終わったあとも、盤面を止めたまま tick を数え、何もしない操作と要約を送り続けます。
やめると、試合を決めた決着が端末ごとに食い違ったときに、中継の突き合わせが揃わず、
ずれに気づけません。

tick T に押した操作は、全員の手元で tick T+3 に効きます（入力遅延 3 tick＝50ms）。
同じ LAN の往復は 1〜3ms なので、相手の操作は使う前に届き、待って止まることはほとんどありません。

⚠️ 始めた直後は、最初の3 tick ぶんの操作を「何もしない」で埋めて送ります。
これが無いと、tick 0 の操作は誰も送らない（最初に送るのは tick 3 の操作）ので、
全員が互いを待ったまま止まります。

### 時刻は試合通算の tick で数える

盤面の時刻（`world.now`）は、ラウンドごとに 0 へ戻り、決着のあとの待ち（2秒）の間は止まります。
同じ `world.now` が試合の中で何度も現れるので、通信の時刻には使えません。
`LockstepDriver.elapsed`（試合が始まってから進めた tick の数）を使います。決着のあとの待ちの間も、
試合が終わったあとも進みます。試合の最中は `GameSession.elapsed` と同じ値です。

操作の記録（`InputLog`）と、記録を流す窓口（`ReplayIntentSource`）も同じ時刻で数えます。
そのため、通信対戦で届いた操作の記録を、1台の試合で流し直せます（ラウンドをまたいでも同じ試合になる）。
ただし条件が2つあります。

- CPU の枠の操作は記録に無いので、同じ設定（`LanSettings`）から `lanCpuSource` で作り直します
- ⚠️ 途中で抜けた人がいた試合は流し直せません。本物の端末は、抜けた人を `lastTick` の次の tick から
  CPU に替えますが、記録には `lastTick` も替えた事実も残りません。記録はその人の最後の操作を返し続けるので、
  例外も出ずに別の試合になります

## 中継はゲームを知らないまま、ずれを見つける

中継サーバ（[server/](../../server/) の `LockstepRoom`）は、届いた操作を送り主以外の全員へ配るだけで、
操作の中身もゲームのルールも知りません。

それでも、端末ごとに試合がずれたことは見つけられます。各端末は 20 tick ごとに
状態の要約（`hashWorld`）と、試合の乱数を引いた回数を送ります。中継は、同じ tick の数が
全員で一致するかだけを比べ、食い違えば全員に知らせて試合を止めさせます。

中継は、その数が何を要約したものかを知りません。**試合を決定的に作ったことで、
ゲームを知らないプログラムが、ゲームの不具合を 20 tick（1/3 秒）以内に見つけられる**ようになりました。

乱数を引いた回数を別に送るのは、ずれの種類を絞るためです。要約だけでは「どこかが違う」ことしか
分かりませんが、回数が違えば「どこかで乱数を余計に引いた（引かなかった）」ことまで分かります。

## 抜けた人は、全員が同じ tick から CPU に替える

中継は1秒ごとに各端末の応答を確かめ、2秒応答が無ければ回線が切れたとみなします。
ロックステップでは、切れた人の操作が止まると残りの人も待って止まり、何も送らなくなるので、
原型の中継が頼っている「送れなければ外す」では気づけないためです（確かめないと、
WebSocket のライブラリ（websockets）が既定で行う生存確認（20秒ごとに確かめ、返事を20秒待つ）が
切るまでの30〜50秒、全員の画面が止まります）。

回線が切れた人の操作は、端末ごとに届いたところまでが違いえます。それぞれが
「届いたところまで」で CPU に替えると、替えた tick が端末ごとに食い違って試合がずれます。

そこで中継が、抜けた人の操作を最後に配った tick（`lastTick`）を全員に知らせます。
全員が `lastTick` までは届いた操作で進め、その次の tick から CPU に替えます。

⚠️ `lastTick` には、中継が配っている最中の操作も含めます。配っている最中の操作は、残った全員に
届きます。含めずに1つ前を知らせると、先にその操作を受け取った端末は本人の操作で、
あとで受け取る端末は CPU で、同じ tick を進めてしまいます。

## 約束を2つの言語で書いている

メッセージの形は、端末側（TypeScript の `src/net/protocol.ts`）と中継側
（Python の `server/src/animal_bomber_server/protocol.py`）に1つずつ書いてあります。
片方だけ直すと、相手が知らない項目を送ったり、必要な項目を待ち続けたりします。

食い違いは検査で見つけます。

| 突き合わせるもの | 検査 |
|---|---|
| TypeScript の表と型 | `tests/net/protocol.test.ts`（型のテスト） |
| TypeScript の表と Python の表 | `server/tests/test_protocol_sync.py`（`protocol.ts` を読んで比べる） |
| Python の表と、中継が実際に読み書きする項目 | 同上 |

## 遊び方

この版をビルドしてから、中継サーバを1台の Mac で立てます。中継は、この版のビルドの出力（`ts/dist`）を
`/ts/` の下で配ります。`/` とそれ以外の道は、これまでどおり原型の HTML です。

```sh
npm --prefix ts run build                                  # この版を ts/dist に出す（直したら出し直す）
uv --directory server run python -m animal_bomber_server   # 中継（8777 番）。この版も配る
```

- 中継を立てた Mac：`http://localhost:8777/ts/` を開き、タイトルの「通信対戦」を選ぶ
  （`http://localhost:8777/ts/?relay` を開くのと同じ）。この Mac のブラウザが 1P（ホスト）になる
- ほかの Mac：`http://<中継を立てた Mac の名前>.local:8777/ts/` を開き、同じく「通信対戦」を選ぶ
- 開発中は、開発サーバ（`npm --prefix ts run dev -- --host`、5173 番）から開いても同じ中継につながります
  （開発サーバは既定で `.local` の名前でのアクセスを断るので、`vite.config.ts` で許可してある）
- 中継を `--port` で別のポートに立てたときは、そのポートで `/ts/` を開く。中継から配られたページは、
  ページと同じポートの中継につなぐ（`WebSocketLink.ts` の `defaultRelayAddress`）。開発サーバから開いたページは 8777 番につなぐ
- 1P のロビーで、4つの枠それぞれの動物・CPU の強さ・体力と、ルールを決める。ほかの人は待つ
- 全員がつながったら、1P が「はじめる」をクリックする。人間のいない枠は CPU が受け持つ
- 開始位置はプレイヤー番号の順（1P 左上・2P 右上・3P 左下・4P 右下。原型と同じ）。1台で2人＋CPU2体の
  ときだけ 2P が右下から始まるが、その並び（`MatchConfig` の `spawnOrder`）は通信対戦では読まない
  （`parseLanSettings`）。全員が中継から届いた同じ1通を同じく読むので、送り手が並びを付けていても試合はずれない

⚠️ 1P は中継サーバを立てた Mac のブラウザに決まります（原型と同じ）。その Mac でページを開かないと、
誰も試合を始められません。

もう一度遊ぶときは、**全員がページを閉じてから**開き直します。中継は、前の試合にいた人が1人でも
つながっている間は、新しい接続を断ります（途中から入った人の操作は、誰の手元の試合にも入れられない
ため）。先に開き直して断られた人は、全員が閉じたあとにもう一度読み込み直します。

## まだ無いもの

- 接続を保ったままの再戦。いまは全員がページを閉じてから開き直します。中継に「試合を終えて
  部屋を戻す」約束を足す必要があります
- 始まる前に、ホストが決めた設定をゲストの画面へ見せること（設定は試合が始まるときに届きます）

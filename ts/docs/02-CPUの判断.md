# CPU の判断

CPU は、キーボードやゲームパッドと同じく **1 tick ごとに入力（`PlayerInput`）を返すだけ**の
部品です（`src/ai/CpuInputSource.ts`）。ゲーム本体からは、人間と区別がつきません。

---

## 判断を、優先順に並んだ独立した規則に分けた

原型の判断は、140 行の関数の中に `if` を順に並べたものでした。規則を1つ足したり
外したりするには、関数全体を読んで、どこに差し込むとどの分岐が飛ばされるかを
確認する必要がありました。

この版では規則を1つずつ独立させ、配列に並べています（`src/ai/behaviors/DefaultChain.ts`）。

```ts
export const DEFAULT_CHAIN = [
  FLEE,           // 爆風が届くマスにいたら逃げる
  DODGE_LEEK,     // 外周から飛んでくる葱の射線から外れる
  ATTACK_IN_LINE, // 射線に入った相手を狙う
  COLLECT_ITEM,   // 近くのアイテムを拾う
  HUNT,           // 相手に近づく
  BREAK_BLOCKS,   // ブロックを壊しに行く
  WANDER,         // やることが無ければ歩き回る
];
```

先頭から順に試し、最初に計画を返した規則が採られます。**配列の順番がそのまま
優先順位**で、どの規則もほかの規則の存在を知りません。

これで何が楽になるかは、原型で失敗した規則を試すとよく分かります。原型では
「袋小路では爆弾を置かない」を加えたところ、開幕はどこも袋小路なので、強い CPU が
40 秒のあいだ1個も置かなくなりました。この版では、その規則を配列に1行足すだけで
失敗を再現できます（`tests/ai/cpu.test.ts` の「規則を1つ足すだけで振る舞いが変わる」）。
外すのも1行です。

段階8では、外周から飛んでくる葱をよける規則（`DODGE_LEEK`）を、爆風から逃げる規則の
次に1行足しました。ほかの規則には触れていません。規則が無いと葱に当たり、足すとよける
ことを、並びを替えた2つの CPU で確認しています（`tests/ai/negibon-cpu.test.ts`）。

## 外周にいる CPU

倒れて外周へ回った CPU（葱ボン）は、判断の並びを使いません。盤面の上の判断とは
やることが違うので、別の操縦（`src/ai/NegibonPilot.ts`）に任せます。操縦は原型の
cpuNegiUpdate と同じ動きにしてあります。

1. 射線上に相手がいて、射程の内で、間に柱・ブロック・爆弾が無ければ、0.6 秒狙いを定めてから撃つ
2. いなければ、0.25 秒ごとに進む向きを選び直し、次の選び直しまで同じ向きで外周を進む

外周のどの辺で何を押すとどちらへ進むかは、人間の操作と同じ変換から逆算しています。
別に表を持つと、人間と CPU で進み方が食い違ったときに気づけません。

狙う相手・寄る先・向きの決め方は原型のままです。そのため、撃てない位置へ寄ることや、
当たらない位置から撃つことがあります。

| 原型と同じにしたこと | 起きること |
|---|---|
| 狙う相手は盤面にいる全員。無敵中・突進中・跳び上がっている相手も狙う | 葱は通り抜けるので、撃つ間隔を無駄にする |
| 寄る先は、いちばん近い相手のマスに向き合う4辺の位置のうち、外周を回っていちばん近いもの。射程も柱の陰も見ない | いちばん近い辺から撃てないと、そこで行ったり来たりするか止まって、撃たない（残り60秒で外周が閉じるまで続くことがある） |
| 寄る先は相手のマスの中央に向き合う位置 | マスの中央からずれて立つ相手は、着いても射線に乗らないことがある |
| 進む向きは選び直しのときだけ決める。そのとき残りが 0.25 マス未満なら止まる | 寄る先を行き過ぎては戻る。往復の途中で射線に乗れば、止まって撃つ |
| 射線に乗っているとみなす幅は 0.3 マス（葱の当たり判定は 0.28 マス） | ずれが 0.28〜0.3 マスの位置からは、止まっている相手にも当たらないのに撃つ |

この版の途中までは、これらを原型の不具合として修正していました（撃てる位置だけを探して寄る、など）。
原型に合わせる方針にしたので、原型の動きに戻しました。構えてから撃つまで（原型は 36 フレーム目、
この版は 37 tick 目）と、向きを選び直す間隔（原型は 16 フレーム、この版は 15 tick）だけは、原型が
1/60 秒を小数で数え続けたための1フレームの差で、この版は実数で数えた tick のままです。

盤面にいる CPU の葱のよけ方も原型のままです。飛ぶ向きと直角の2マスを、横に飛ぶ葱なら下→上、
縦に飛ぶ葱なら右→左の決まった順に試し、通れて爆風の届かない最初のマスへよけます。自分が射線の
どちら側に立っているかも、いまの位置で当たるかも見ないので、射線の左（横に飛ぶ葱なら上）に立っていると、
右（下）へよけて射線を横切ることがあります。この版の途中までは射線から離れる側を先に試し、いまの位置で
当たらなければ射線を横切らないようにしていましたが、原型に合わせました。

外周から葱を当てて盤面へ戻った CPU も、延長戦に入った CPU も、記憶を捨てません（原型と同じ）。
当てた相手の位置や開始位置へ移ったあとも、次に考え直すまでは移る前の経路の先のマスへ1軸ずつ歩き、
置き直さない記憶・爆弾を控える残り・判断の間隔の揺らぎも続けて使います。原型が CPU の記憶を作り直すのは
ラウンドの始まりだけです。外周の操縦の記憶（選び直しの残りと向き）も、同じラウンドの2度目の外周へ持ち越し、
外周へ回るときは構えの溜めだけを戻します（原型の toNegibon と同じ）。

## 動物ごとの違いは「戦い方」として差し込む

原型の CPU には「もぐらなら」「きつねなら」という分岐が8か所ありました。
この版の共通の判断は動物を知りません。原型の分岐はどれも次のどこかに当たるので、
それぞれを `src/ai/tactics/` の戦い方で差し替えます。

| 差し替える点 | 原型の分岐 | 省略したとき |
|---|---|---|
| 考える前の技 | 穴を掘る・舌を伸ばす（使ったフレームはほかに何もしない）・危ないときの突進 | 使わない |
| 歩いたあとの技 | 狐火・粘膜爆弾・撒く | 使わない |
| 爆弾の置き方 | 一列に並べる | 足元に1個 |
| ブロックを壊しに行くときに立つ場所 | 1マス空けた手前に立つ | 壊せるブロックの隣 |
| 壊しに行くときに置くかの見直し | 並べる向きに壊せるブロックが無ければ置かない | 見直さない |
| 振る舞いの最中も考えるか | 突進の最中は考え続ける（掘る・舌の間は待つ） | 待つ |

共通の判断のファイルに動物の名前が1つも出てこないことは、テストで検査しています
（`tests/boundary/guards.test.ts`）。コメントに書いても失敗します。

「いつ突進するか」をルールの層（`Ability`）に置かなかったのは、それがゲームのルールではなく
CPU の考え方にすぎないからです。人間は同じ能力を別の場面で使います。

## CPU は盤面を書き換えない

CPU が受け取る盤面は読むだけです。型の `Readonly` は浅いので、中の配列の書き換えまでは
止められません。そこで、入力を返す前と後で**状態の要約（ハッシュ）が変わらない**ことを
テストで確認しています。要約には試合の乱数を取り出した回数も入っているので、
CPU が試合の乱数に触れていないことも同時に分かります。

CPU は自分専用の乱数を持ち、`Math.random` は lint で禁じています。CPU の判断も種から
決まるので、同じ種なら CPU どうしの試合は何度やっても同じになります。通信対戦で
各端末が CPU を動かしても、全員が同じ手を得ます。

## 原型の CPU と同じ手を、入力で指す

原型の CPU は操作を経由せず、関数を直に呼んでプレイヤーを動かしていました（`cpuUpdate`・`planCPU`）。
この版の CPU は人間と同じく入力を返します。そのうえで、原型の CPU と同じ手になるように、
1 tick の中の判断の順も規則も原型に合わせています（`CpuInputSource` の説明に順を書きました）。

| 原型の CPU が直に呼んでいたもの | この版の CPU が押すもの |
|---|---|
| `movePlayer`（経路の次のマスの中央へ。斜めは横に丸める） | 向き（`PathFollower`。着いたと見なす距離・片方の軸だけを押す距離も原型と同じ） |
| `placeBomb` | 爆弾のボタンを押した瞬間 |
| `foxLineShot`（一列） | 技のボタンを押した瞬間 |
| `startTongue`（舌） | 技のボタンを押した瞬間 |
| `useSpecial`（とくぎ。長押しの待ちも、押した瞬間の通常技も無い） | とくぎを直に出すボタン（`PlayerInput.special`。人間の操作には割り当てていない） |

ゲームの側は、入力を 動く → 爆弾 → 技 の順で適用するので、原型の CPU が1フレームの中で
歩く → 置く → とくぎ と呼んでいたのと同じ順になります。ぞうは原型どおり、危ないマスに立っているときに
突進で逃げます（長押しを待たないので間に合います）。

入力で表せないために残った違いがあります。

| | 原型 | この版 |
|---|---|---|
| 操作の反転（悪いアイテム） | CPU には作用していなかった（操作を経由しないため） | 作用してしまうので、CPU が知っていて打ち消す（原型と同じ強さに揃える） |
| とまれない（悪いアイテム） | CPU には作用していなかった（止まれないのは人間の操作の処理だけだった） | 移動の処理が誰にでもかけるので、CPU も止まれない。入力では打ち消せない |
| きつねの一列の本数 | 手持ち全部で逃げ切れないとき、本数を減らして逃げ切れる本数だけ並べる（`p.lineCap`） | 本数は入力（ボタンの組）に載らないので絞らない。手持ち全部で逃げ切れなければ置かない |
| 同じボタンを続けて押す | 続くフレームで関数を呼べた | ボタンは押した瞬間にだけ有効なので、前の tick に押したボタンは次の tick に回す（そうなる場面はほとんど無い） |
| 判断に使う盤面 | 1フレームの中で、歩いたあと・置いたあとの盤面を見ることがある | tick の始めの盤面だけを見る |

葱ボン（外周の操縦・盤面での葱のよけ方）と、延長戦に入ったとき・外周から戻ったときの記憶の扱いは、
Python 版に葱ボンを移す前に原型に合わせました（上の「外周にいる CPU」の節）。

## 見積もりと実際を、同じ関数にする

CPU は「あと何 tick でこのマスに爆風が届くか」の地図（`src/domain/query/DangerMap.ts`）の上で
すべてを判断します。この地図が実際の爆発と食い違うと、CPU は安全だと思って立った所で倒れます。

そこで、爆風の届く範囲（`query/BlastReach.ts`）を1か所に置き、**爆発の処理と CPU の見積もりが
同じ関数を使う**ようにしました。食い違いを注意ではなく構造で防いでいます。

危ないかは、原型どおり立っているマス（体の中心のマス）だけで見ます。経路は次のマスの中央から
0.15 マス以内に来てから先へ進むので、経路の終わりで立ち止まった体が隣のマスにはみ出すことはありません
（爆風の当たり判定は中心から 0.14 マス）。この版の途中には、マスに入った直後に立ち止まる経路の追い方を
していた時期があり、はみ出した体で爆風に当たって、被弾のうち自爆が 7 割を超えていました。

## 画面なしで強さを測る

ルールの層も CPU も画面を使わないので、CPU どうしの試合を画面なしで実行できます。
4体の試合 43,000 tick が 1 秒かかりません。

`tests/ai/balance.test.ts` では、両端の強さ（おに と よわい）で勝ち数が逆転していないことを
常に確認しています。数値を調査するための計測も同じファイルにあります。

```sh
MEASURE=1 npx vitest run tests/ai/balance.test.ts
```

### まだ目安に届いていない数値

- 強い CPU の被弾のうち、自爆の割合（原型の目安は半分未満）
- 4段階すべての強さの順（両端は揃っているが、中の2段が動物の組み合わせで入れ替わる）

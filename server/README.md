# server — LAN 対戦の中継サーバ

同じネットワークにいる端末どうしで対戦するための中継サーバです。Python で
書かれており、ゲームの HTML を配る役と、参加者の間でメッセージを転送する役を
兼ねます。両方を**同じポート**で扱います。

[`legacy/`](../legacy/) の HTML 版と、[`ts/`](../ts/) の TypeScript 版が使います。
2つは中継のやり方が違うので、つなぐパスで部屋を分けています。

| パス | 部屋 | 使う版 | 中継のやり方 |
|---|---|---|---|
| `/` | `relay.Room` | HTML 版 | ホスト権威。ホストだけが試合を進め、盤面を全員へ配る |
| `/lockstep` | `lockstep.LockstepRoom` | TypeScript 版 | ロックステップ。全員が試合を進め、1 tick ぶんの操作だけを全員へ配る |

ページも同じポートで配ります。`/ts/` の下では TypeScript 版のビルドの出力（`ts/dist`）を、それ以外の道では
HTML 版を返します（`http.py`）。

---

## Design Choice — この実装で決めたこと

### 1. 試合の中身を1行も知らない

中継は「どの接続が何番のプレイヤーか」の対応だけを持ち、届いたメッセージを**中身を見ずに**転送します。
プレイヤー番号（コード上の名前は `seat`）は、つないできた接続に中継が割り当てる 0〜3 の番号で、
ゲームの側はそれをそのままプレイヤー番号として使います（番号 N の端末がプレイヤー N を操作する）。
爆弾が何秒で爆発するかも、どの動物が何をするかも知りません。

理由は、知った瞬間に**同期を保つべきゲームの実装が2つになる**からです。
クライアント側でルールを1つ変えるたびに、サーバ側の解釈も合わせて直す必要が
生まれます。中身を見ない限り、その負債は発生しません。

### 2. 静的配信と WebSocket を同じポートに載せる

`websockets` ライブラリの HTTP フック（WebSocket へ昇格しないリクエストを
横取りできる仕組み）を使い、通常の HTTP リクエストには HTML を返します。

これにより、参加者に伝える URL が1つで済みます。ポートを2つ使うと、
ファイアウォールの許可も接続案内も2倍になります。

**ゲストはホストから HTML をダウンロードして遊ぶため、版のずれが構造的に
起きません。** これがブラウザ経由で配る方式の実質的な利点です。

### 3. 送信の失敗を、例外ではなく沈黙として扱う

（ホスト権威の部屋の話。ロックステップの部屋は、送る量が少なくてこの方法では気づけないので、
4 で別の方法をとっています。）

**この設計は実際の不具合から導かれたものです。**

当初、中継は各参加者への送信を1人ずつ順番に待つ形で書かれていました。
この形は、参加者の1人が回線を切ったときにホストまで巻き添えで切断します。

原因は、接続が切れても送信側にはすぐ分からないことにあります。Wi-Fi が
切れた端末は接続の終了を通知しないため、送信処理は例外を出さずに
**そのまま止まります**（ライブラリ側の送信待ち行列が埋まり、以降の読み取りも
止まるため、応答確認が返らなくなってホストが切断される）。

対策として、送信を並行に行い、それぞれに制限時間を設けました。時間内に
送れなかった参加者だけを切り離し、ホストは決して切りません。

```python
SEND_TIMEOUT = 0.1  # 1つの接続への送信をあきらめるまでの秒数
```

⚠️ この種の不具合は、送信に例外を投げさせるテストでは再現できません。
例外だけを模した検査は `try` を1つ足すだけで通ってしまい、本当の症状
（止まったまま戻らない）が残ります。テストでは**応答せず黙り続ける相手**を
用意して確認しています（`tests/test_relay_dead_guest.py`）。

### 4. ロックステップの部屋は、ゲームを知らないまま状態のずれを見つける

ロックステップの部屋も、操作の中身は読みません。読むのは tick の番号と、各端末が
20 tick ごとに送ってくる状態の要約（ハッシュ）と乱数を引いた回数、それと、いまの試合のものかを
見るための試合の番号だけです。同じ tick の
報告が全員ぶん揃ったら数が一致するかを比べ、食い違えば全員に知らせて試合を止めさせます。
その数が何を要約したものかは知りません。

回線が切れた人は、1秒ごとに応答を確かめて見つけます。ロックステップでは、切れた人の入力が
止まると残りの人も待って止まり、何も送らなくなります。送る処理が詰まらないので、3 の方法では
気づけません。応答が2秒無ければ切り、残った人に「その人の入力を最後に配った tick」を
知らせます。全員がその次の tick から CPU に替えるので、替わる瞬間が端末ごとに揃います。

メッセージの約束は `protocol.py` と TypeScript 版の `ts/src/net/protocol.ts` に1つずつ
書いてあり、`tests/test_protocol_sync.py` が突き合わせます。

## 構成

| ファイル | 役割 |
|---|---|
| `main.py` | 起動の入口。ポートの確保、静的配信と中継の組み立て、接続1本ぶんの扱い |
| `http.py` | HTML の静的配信。WebSocket へ昇格しないリクエストを受け持つ |
| `relay.py` | プレイヤー番号の割り当てとメッセージ転送。ゲームのルールを持たない中核 |
| `lockstep.py` | ロックステップの部屋。操作を全員へ配り、状態の要約を突き合わせる |
| `protocol.py` | ロックステップのメッセージの約束（TypeScript 版と同じもの） |
| `netinfo.py` | この端末を LAN 上でどう指せばよいか（`.local` 名と IP アドレス）を調べる |
| `ui.py` | 起動中であることを示す小さな窓。接続用の URL と終了ボタンを出す |

## How-to — 動かし方

```sh
uv sync
uv run python -m animal_bomber_server          # 既定のポート 8777 で起動
uv run python -m animal_bomber_server --help   # ポート・HTML・TypeScript 版の置き場所の指定
```

TypeScript 版は、先に `ts/` で `npm run build` しておくと、`/ts/` の下で配ります
（`http://<端末名>.local:8777/ts/`）。ビルドしていなければ、`/ts/` はビルドの仕方を案内します。
⚠️ デスクトップアプリ（下）には、TypeScript 版をまだ入れていません。アプリで `/ts/` を開くと、入れていないことを
案内します（リポジトリでビルドしても、アプリはそれを読みません）。入れるには spec の `datas` に
足して作り直し、実機で確かめる必要があります。
中継を `--port` で別のポートに立てたときは、そのポートで `/ts/` を開きます（ページと同じポートの中継につなぎます）。

起動すると接続用の URL が2種類表示されます。

```
http://<端末名>.local:8777
http://192.168.x.x:8777
```

`.local` の名前は同じネットワーク上の Mac どうしなら設定なしで通りますが、
VPN・アクセスポイントの端末間通信の遮断・ネットワークの分割があると
解決できません。**IP アドレスは対等な代替手段**であり、うまくいかないときの
予備ではなく、環境によってはそちらが主になります。

### デスクトップアプリとして配る

`animal-bomber-server.spec` が PyInstaller のビルド定義です。`--onedir` を
選んだ理由、実行体のファイル名を ASCII に固定している理由（日本語名だと
署名時にクラッシュする）は、spec ファイル冒頭に記録してあります。

```sh
uv run pyinstaller animal-bomber-server.spec
codesign --force --deep -s - dist/*.app
```

macOS で初回に通過する必要のある確認が3つあります。

| | 表示されるもの | 対応 |
|---|---|---|
| 未署名のアプリ | 「開発元を確認できないため開けません」 | 初回だけ右クリックから開く |
| ファイアウォール | 「接続を受け入れますか」 | 許可する。⚠️ 許可しないと**他の端末からは接続が拒否されるだけで、他に何の症状も出ない** |
| ローカルネットワーク | 「ローカルネットワーク上のデバイスの検索を求めています」 | 許可する |
